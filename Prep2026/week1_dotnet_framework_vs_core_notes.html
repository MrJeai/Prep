01

The Big Picture & Timeline

What .NET is, the two platforms, and why the naming is confusing
1.1 — First, what does the word ".NET" actually mean?

Before comparing "Framework" and "Core", you have to be clear about what ".NET" itself is, because the word gets used loosely. .NET is a development platform — not a single program, but a bundle of three things that always travel together:

⚙️
A Runtime
The engine that actually executes your compiled code, manages memory (garbage collection), and handles threading. This is the CLR in Framework and the CoreCLR in Core.
📚
A Library Set
Thousands of pre-built classes you call every day — List<T>, String, File, HttpClient. Collectively the Base Class Library (BCL).
🛠️
Languages + Compiler
C#, F#, and VB.NET, plus the compiler (Roslyn) and tooling that turn your source code into something the runtime can run.
📖 Definition
.NET Framework and .NET Core are two different implementations of this same idea — two separate engines and library sets that both run C#. They are siblings, not versions of each other. You cannot "upgrade" Framework to Core by changing a number; they are built on different foundations, which is the whole reason this comparison matters.

A useful one-line mental model to carry through the rest of these notes: both platforms run C#, but Framework is the old Windows-only engine from 2002, and Core is the modern, cross-platform, rebuilt-from-scratch engine that replaced it.

1.2 — What is .NET Framework? (the original, 2002)

.NET Framework was Microsoft's original .NET platform, first released in 2002. For nearly 15 years it was ".NET" — there was no other option. It was designed in an era when "a server" almost always meant "a Windows server running IIS", so the entire platform was built tightly around Windows.

Three properties define it, and each one later became a limitation:

  • ▸Windows-only. It uses Windows-specific APIs deep inside, so it physically cannot run on Linux or macOS.
  • ▸Machine-wide and pre-installed. It ships as part of Windows itself. One copy is installed for the whole machine, and every app shares it.
  • ▸Monolithic. It is one giant, indivisible package. You reference "the Framework" and get everything, whether you use it or not.

Its final version is 4.8 / 4.8.1. Microsoft has stated it is "done" — it is still supported (it ships with Windows and gets security fixes), but it will receive no new features ever again. This is the platform your current legacy stack runs on.

📝 Note for your situation
Your current work (.NET Framework, SSRS, XML-based frameworks, workflow systems) lives entirely in this world. Nothing about it is "wrong" — these apps run fine and will keep being supported. But because Framework is frozen, the market has moved to Core, and that gap is exactly what these 12 weeks are designed to close.
1.3 — What is .NET Core? (the rebuild, 2016)

Around 2014–2016, Microsoft made a bold decision: rather than keep patching the aging Framework, they would rewrite the platform from scratch with a modern design and ship the first result as .NET Core 1.0 in June 2016. The goals were explicit and they shaped everything:

🌍
Cross-platform
Run the same app on Windows, Linux, and macOS — essential for Docker, the cloud, and cheaper Linux hosting.
🔓
Open source
Developed in the open on GitHub, with the community able to read, contribute, and file issues — the opposite of the closed Framework.
🧩
Modular
Ship only the pieces an app needs as small NuGet packages, instead of one giant install. Smaller, faster, deployable per-app.
⚡
High-performance
A new JIT, a rewritten web stack (Kestrel + ASP.NET Core), and a relentless focus on speed and memory — now among the fastest mainstream runtimes.

Because it was a clean rewrite, the team was free to fix old mistakes: they baked dependency injection into the core, replaced the clumsy web.config XML system with a flexible configuration model, built a fast cross-platform web server (Kestrel), and unified MVC, Web API, and Razor Pages into one framework (ASP.NET Core). These are the things your roadmap spends Week 1–4 on, and they exist because Core was a rewrite, not a patch.

1.4 — The naming mess, explained once and for all

This trips up almost everyone, so it is worth getting straight. The name changed twice, which is why you'll hear ".NET Core", ".NET 5", ".NET 8" and wonder if they are different things. They are the same lineage. Here is the actual timeline:

The original. Evolves up to 4.8.1, then frozen. Windows-only.

The cross-platform rewrite. Called "Core" through version 3.1.
↓

💡 The one sentence to remember
".NET Core", ".NET 5", ".NET 6", ".NET 8" are all the same modern platform — Microsoft just dropped the word "Core" after version 3.1 and skipped "4". So in 2025+, when someone says "I work in .NET 8", they mean modern Core. ".NET Framework 4.x" is the separate, frozen, old platform. Modern ≠ a higher Framework number; it's a different lineage entirely.
⚠️ Common confusion to avoid
.NET Framework 4.8 sounds "newer" than .NET Core 3.1 because 4.8 > 3.1. It is not. They are different products on different version tracks. .NET 5 deliberately jumped past 4 precisely so nobody would think ".NET 5" was an upgrade of "Framework 4.x".
02

Why .NET Core Was Born

The real pain points of .NET Framework that forced a rewrite

Interviewers love this question because it separates people who "use .NET" from people who understand it. If you can explain why Core had to exist, you've shown you understand the engineering trade-offs, not just the syntax. Each pain point below follows the same shape: the limitation → the consequence it caused → how Core fixed it.

2.1 — Pain #1: Windows-only

The limitation: .NET Framework was built on Windows-specific APIs (the Win32 layer, the Windows registry, IIS). Those dependencies are woven so deeply into the runtime that the platform simply cannot run anywhere else.

The consequence: By the 2010s the world had moved to the cloud, and cloud servers overwhelmingly run Linux — it's free, lightweight, and the default for Docker containers. A Windows-only platform meant you were locked into more expensive Windows hosting and couldn't put your app in a small Linux container. For a company running thousands of servers, that's a massive, recurring cost.

💡 How Core fixed it
Core was written to be cross-platform from day one. The same compiled app runs on Windows, Linux, and macOS. This is what makes Docker, Kubernetes, and cheap Linux cloud hosting possible — and it's why "cross-platform" is the headline feature in every Core-vs-Framework answer.
2.2 — Pain #2: Welded to IIS and System.Web

The limitation: In old ASP.NET, your web app couldn't run by itself. It needed IIS (Internet Information Services — Microsoft's Windows-only web server) to host it, and the entire request-handling stack lived in a heavy assembly called System.Web that was bolted to IIS.

The consequence: You couldn't run the app outside Windows, couldn't easily self-host it, couldn't unit-test the hosting layer, and you inherited all of System.Web's weight whether you needed it or not. The web pipeline was also rigid — reordering how requests were processed meant fighting HttpModules configured in XML.

💡 How Core fixed it
Core ships its own fast, cross-platform, in-process web server called Kestrel. A Core web app is just a normal program with a Main method that starts a server — it can run standalone, behind nginx, behind IIS as a reverse proxy, or inside a container. System.Web is gone, replaced by the lean, code-driven middleware pipeline (your previous module).
2.3 — Pain #3: One machine-wide copy ("DLL hell")

The limitation: The Framework is installed once for the entire machine, and every application on that server shares the exact same copy. Shared assemblies live in a special system-wide store called the GAC (Global Assembly Cache).

The consequence: If App A needs Framework 4.6 behaviour and App B needs 4.8 behaviour, they fight — because there is only one copy and one GAC for both. Patching the Framework to fix App B could silently break App A. This whole class of problem earned the nickname "DLL hell": you cannot run different versions side by side on the same machine.

💡 How Core fixed it
Core is installed per-application (or even bundled inside the app). App A can ship with .NET 6 and App B with .NET 8 on the same server, fully isolated. There is no GAC. This side-by-side versioning means upgrading one app never endangers another — a huge operational win.
2.4 — Pain #4: Updates installed "in place" and broke things

The limitation: Because the Framework was system-wide, Microsoft updates replaced it in place. Your app didn't choose its runtime version — the machine's current Framework decided it, and that could change underneath you via Windows Update.

The consequence: A perfectly working production app could behave differently after a routine OS patch, because the shared runtime changed beneath it. Teams were terrified of updates, so machines drifted into inconsistent, hard-to-reproduce states.

💡 How Core fixed it
Each Core app pins the exact runtime version it was built and tested against. The runtime travels with the app (or is explicitly chosen), so "works on my machine" actually means "works everywhere" — the same bits run identically in dev, CI, and production. This predictability is the foundation of modern CI/CD and containers.
2.5 — Pain #5: Slow, Windows-tied release cadence

The limitation: Framework releases were chained to Windows release cycles, so meaningful new versions arrived years apart.

The consequence: .NET fell behind faster-moving ecosystems. New language features, performance work, and APIs were bottlenecked behind the OS schedule.

💡 How Core fixed it
Core decoupled from Windows entirely and now ships a major version every November, like clockwork. Even-numbered releases are LTS (longer support); odd ones are shorter-lived feature releases. Predictable, frequent, fast.
2.6 — Pain #6: Monolithic and heavy

The limitation: Reference "the Framework" and you got all of it — every API, used or not — as one indivisible block of hundreds of megabytes.

The consequence: Large deployments, slow startup, and no way to trim what you didn't use. Terrible for containers, where image size directly affects cost and deploy speed.

💡 How Core fixed it
Core's library is modular NuGet packages: you pull in only what you use. Combined with trimming (removing unused code) and self-contained / single-file / Native AOT publishing, you can ship tiny, fast-starting apps — ideal for microservices and serverless.
🎯 Interview gold — say it like this
"Framework was a Windows-only, machine-wide, monolithic platform welded to IIS, with a slow release cadence and no side-by-side versioning. Those constraints made it unfit for cloud, containers, and Linux. Rather than keep patching it, Microsoft rewrote .NET as a cross-platform, open-source, modular, app-local, high-performance runtime — that rewrite is .NET Core, now just called .NET." That single paragraph answers half the .NET-fundamentals questions you'll get.
03

Under the Hood — Architecture

The runtime, the JIT, the libraries, and how the engine is delivered

To answer the deeper interview questions ("how does it actually run differently?") you need to see inside both platforms. Both follow the same basic flow — your C# is compiled to an intermediate language, then a runtime turns it into native machine code and executes it — but each layer is implemented differently. Let's walk the stack from top to bottom.

3.1 — The shared idea: source → IL → native

This part is the same on both platforms, and it's worth stating because it grounds everything else:

1
You write C#
Human-readable source code.
↓
2
Compiler (Roslyn) → IL
Compiles to Intermediate Language (IL/MSIL) — a CPU-neutral bytecode stored in a .dll or .exe assembly. IL is not yet machine code.
↓
3
Runtime + JIT → native machine code
At runtime, the JIT (Just-In-Time) compiler converts IL into native CPU instructions, on demand, the first time each method runs.
↓
4
Runtime executes & manages it
The runtime runs the native code while handling garbage collection, type safety, and exceptions.
📖 Definition — Managed code
Because the runtime manages memory and safety for you, .NET code is called managed code. The runtime that does the managing is generically called the CLR (Common Language Runtime). Both platforms have a CLR — they're just different implementations of it.
3.2 — Where they diverge: the runtime & JIT

The engine itself is a different codebase on each platform:

Layer.NET Framework.NET Core / .NET 5+
Runtime (CLR)The original CLR, Windows-only, shipped with the OS.CoreCLR — a re-engineered, cross-platform, open-source runtime.
JIT compilerThe older JIT.RyuJIT — a faster, modern JIT producing better-optimised native code. Also supports Native AOT (compile fully ahead-of-time, no JIT at runtime).
Garbage CollectorMature GC, but tuned for Windows desktop/server.Same GC heritage, heavily tuned for server & container workloads (e.g. respects container memory limits).
📝 Why this matters for performance answers
When people say "Core is much faster than Framework", a big part of the reason lives here: a better JIT (RyuJIT), a container-aware GC, and a rewritten web stack (Kestrel + ASP.NET Core). It's not magic — it's a newer engine.
3.3 — The libraries: BCL vs the unified BCL

Both platforms give you a Base Class Library (BCL) — the built-in types you use constantly. But they are separate implementations:

  • ▸Framework BCL: huge, mature, but Windows-bound and frozen. Includes Windows-only pieces (WinForms, WPF, parts of System.Web) baked in.
  • ▸Core BCL (originally "CoreFX"): rebuilt to be cross-platform and shipped as modular NuGet packages. Windows-only UI tech is optional and only available when you target Windows.

Most everyday APIs — collections, LINQ, async/await, strings, streams — exist in both and behave the same. The differences show up at the edges: Windows-specific APIs, the old config/web stack, and a handful of legacy technologies (covered in Chapter 6).

3.4 — How the engine reaches the machine (the biggest practical difference)

This is the difference you can feel as a developer, and a frequent interview probe:

.NET Framework — Machine-wide
  • Installed once, system-wide, as part of Windows.
  • Shared assemblies live in the GAC.
  • Every app on the box uses the same copy.
  • No side-by-side versions → "DLL hell".
  • Updated in place by Windows Update.
.NET Core — App-local
  • Installed per-app, or bundled inside the app.
  • No GAC. Dependencies are NuGet packages next to your app.
  • Each app pins its own runtime version.
  • Full side-by-side versioning on one machine.
  • You control exactly which runtime ships.
💡 The mental image
Framework is like a shared building utility (one water supply for every flat — change it and everyone is affected). Core is like each flat having its own self-contained tank — total isolation, no one else affected when you change yours.

4.2 — The three rows interviewers dig into
① Performance — don't just say "faster"
Back it up: Core is faster because of the RyuJIT compiler, a garbage collector tuned for server/container workloads, the lightweight Kestrel web server, and a web stack rewritten to minimise allocations. ASP.NET Core consistently ranks among the fastest mainstream web frameworks in public benchmarks. "Faster because newer engine + leaner web stack" is the answer.
② Deployment — the model genuinely changed
Framework apps assume the runtime is already on the server. Core apps can be framework-dependent (small; needs runtime installed) or self-contained (bundles the runtime inside the app, so the target machine needs nothing pre-installed) — plus single-file and Native AOT options. This flexibility is what makes Core ideal for Docker and serverless. (Details in Chapter 5.)
③ Dependency Injection & Configuration — built in vs bolted on
In Framework you reached for third-party DI containers and wrestled with web.config XML. Core bakes DI and a layered configuration system into the framework itself — they're not optional add-ons, they're how the framework is designed to be used. This is why your roadmap treats DI and configuration as core Week-1 skills.
⚠️ Nuance that scores points
Don't say "Core is just better, use it for everything." The mature answer: for any new project, choose modern .NET — it's faster, cross-platform, and where the future is. But some legacy tech only exists on Framework (WebForms, server-side WCF, Windows Workflow Foundation), so an existing Framework app that depends on those may stay there until those parts are re-architected. Knowing when not to migrate shows real engineering judgement.

How a Modern .NET App Runs

The project file, deployment models, TFMs, and .NET Standard
5.1 — The project file got radically simpler

One of the first visible differences when you open a modern project is the .csproj file. The old Framework format listed every single file explicitly and was painful to edit by hand. The modern SDK-style format infers files automatically and is tiny:

XMLMyApp.csproj — modern SDK-style
<Project Sdk="Microsoft.NET.Sdk.Web">
  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
  </PropertyGroup>

  <!-- NuGet dependencies are simple one-liners -->
  <ItemGroup>
    <PackageReference Include="Microsoft.EntityFrameworkCore.SqlServer" Version="8.0.0" />
  </ItemGroup>
</Project>

The <TargetFramework>net8.0</TargetFramework> line is the single most important line in the file — it declares which platform and version you're building for. That value is called a Target Framework Moniker (TFM).

📖 Definition — TFM
A TFM is a short code identifying the target platform: net8.0 (modern .NET 8), net48 (Framework 4.8), netstandard2.0 (.NET Standard). Add a platform suffix like net8.0-windows when you need Windows-only APIs (e.g. WPF).
5.2 — Two ways to deploy (a Core-only superpower)

Framework had essentially one deployment story: "make sure the right Framework is installed on the server first." Core gives you a choice, and interviewers like to hear you know both:

Framework-dependent
  • Ships only your code.
  • Relies on the .NET runtime being already installed on the target.
  • Pro: tiny output.
  • Con: the correct runtime must exist on the machine.
Self-contained
  • Bundles the runtime inside your app.
  • Target machine needs nothing pre-installed.
  • Pro: runs anywhere, version fully pinned.
  • Con: larger output.

On top of these, modern .NET adds single-file publishing (one executable), trimming (strips unused code to shrink size), and Native AOT (compiles fully to native ahead of time — no JIT, near-instant startup, tiny footprint). These are exactly what make small, fast container images and serverless functions practical.

5.3 — .NET Standard: the bridge between the two worlds

During the years when Framework and Core coexisted, library authors had a problem: how do I write one library that works on both? The answer was .NET Standard.

📖 Definition — .NET Standard
.NET Standard is not a runtime you can run. It's a formal specification of a set of APIs that every .NET platform promises to implement. If you build a class library targeting netstandard2.0, it can be referenced by both a Framework app and a Core app — because both guarantee those APIs exist.

Think of it as a contract, not an engine. It let teams share business-logic libraries across the old and new worlds during the transition.

📝 Is it still relevant in 2025?
Mostly historical now. Since .NET 5 unified everything, new code just targets net8.0. You still reach for netstandard2.0 in one case: writing a shared library that must also be consumed by a legacy .NET Framework app. Otherwise, prefer net8.0.
06

Migrating Legacy → Modern

The chapter most relevant to your own background

You currently work on .NET Framework, so this chapter is doubly useful: it's a real interview topic and it reframes your existing experience as an asset. A candidate who can talk about "moving a real legacy system to modern .NET" sounds far more senior than one who only knows greenfield tutorials.

6.1 — When to migrate, and when not to

Migrate when you want cross-platform/Linux hosting, smaller containers, better performance, modern libraries, or simply to stay on a supported, evolving platform. Think twice when the app is stable, rarely changed, and depends heavily on Framework-only technology — a rewrite may cost more than it returns. Good engineering is knowing the difference; say that out loud in interviews.

6.2 — What ports cleanly vs what does not

Most pure business logic, data access, and class libraries port with little change. The pain is concentrated in a specific set of Framework-only technologies that have no direct modern equivalent:

Legacy technologyStatus on modern .NETModern replacement / approach
Web Forms❌ Not supportedRewrite UI in ASP.NET Core MVC, Razor Pages, or Blazor
WCF (server-side)❌ Not supported as hostgRPC, ASP.NET Core Web API, or the community CoreWCF for clients
Windows Workflow Foundation (WF)❌ Not in modern .NETRe-implement with a modern workflow engine or message-driven design
AppDomains❌ RemovedUse separate processes / AssemblyLoadContext
.NET Remoting❌ RemovedHTTP APIs, gRPC, message queues
web.config behaviour⚠️ ReplacedThe new configuration model (appsettings.json + providers)
Business logic, EF, LINQ, most APIs✅ Ports fineRecompile against net8.0; minor tweaks at most
⚠️ Relevant to your stack
Your background mentions workflow systems and XML-based frameworks. If those rely on Windows Workflow Foundation or Framework-only XML config, they're exactly the kind of thing that doesn't lift-and-shift — they need re-architecting. That's not a weakness to hide; it's a great story: "I worked on a legacy workflow system and understand why moving it to modern .NET requires replacing WF with a message-driven design."
6.3 — A sane migration strategy (the incremental way)

Nobody sensible "big-bangs" a large legacy app. The expected, senior answer is incremental migration:

1
Inventory & assess
Catalogue dependencies and flag the Framework-only tech that can't port directly. Run the .NET Upgrade Assistant / portability analyzer to get a report.
↓
2
Extract shared logic to .NET Standard
Move pure business logic into netstandard2.0 libraries so both the old and new apps can use the same code during the transition.
↓
3
Strangler-fig: migrate piece by piece
Stand up the new Core app alongside the old one and route features over gradually, retiring old endpoints as new ones go live. The old app shrinks until it disappears.
↓
4
Replace the unportable bits
Re-implement WebForms → Razor/Blazor, WCF → gRPC/Web API, WF → message-driven flows, web.config → appsettings.json.
↓
5
Decommission the legacy app
Once all traffic flows through the modern app, retire the Framework version.
📖 Term to drop in interviews — Strangler Fig
The strangler-fig pattern (named after the vine that grows around a tree and gradually replaces it) means building the new system around the old one and migrating functionality bit by bit, instead of a risky all-at-once rewrite. Naming this pattern signals maturity.

Interview Preparation

Questions and model answers at the 4 YOE level
Q1What's the difference between .NET Framework and .NET Core?
A.NET Framework is the original 2002 platform: Windows-only, machine-wide, monolithic, welded to IIS, and now frozen at 4.8.x with no new features. .NET Core is a from-scratch rewrite that is cross-platform (Windows/Linux/macOS), open source, modular, installed per-app with side-by-side versioning, and significantly faster. Since .NET 5 the "Core" name was dropped and it's just called ".NET" — so .NET 5/6/7/8 are the modern continuation of Core, not of Framework.
Q2Why did Microsoft build .NET Core when Framework already existed?
ABecause Framework's core design assumptions no longer fit the modern world. It was Windows-only (but the cloud runs on Linux), machine-wide with no side-by-side versioning (causing "DLL hell"), tied to IIS, monolithic, and slow to release. Rather than keep patching it, Microsoft rewrote .NET to be cross-platform, open-source, modular, app-local, and high-performance — which is what containers, microservices, and cloud hosting demand.
Q3Is .NET 8 the same as .NET Framework 4.8? It has a higher number.
ANo — they're different lineages. .NET 8 is the modern Core line; Framework 4.8 is the legacy line. The higher number is coincidental. Microsoft deliberately renamed Core to ".NET 5" and skipped "4" precisely so people wouldn't mistake it for an upgrade of Framework 4.x. .NET 8 descends from .NET Core 3.1, not from Framework 4.8.
Q4Why is .NET Core faster than .NET Framework?
ASeveral reasons compound: a modern JIT (RyuJIT) that produces better native code, a garbage collector tuned for server and container workloads, the lightweight cross-platform Kestrel web server, and a web stack (ASP.NET Core) rewritten to minimise allocations. It also supports Native AOT for near-instant startup. ASP.NET Core regularly ranks among the fastest mainstream web frameworks in public benchmarks.
Q5What is .NET Standard and is it still relevant?
A.NET Standard is a specification — a contract of APIs that all .NET platforms agree to implement — so a single library targeting it can run on both Framework and Core. It was essential during the transition years for sharing libraries across both worlds. Since .NET 5 unified the platforms, new code just targets net8.0, so .NET Standard is mostly historical. The one remaining use case is writing a shared library that must still be consumed by a legacy Framework app.
Q6What's the difference between framework-dependent and self-contained deployment?
AFramework-dependent ships only your app and relies on the .NET runtime already being installed on the target — small output, but the runtime must exist. Self-contained bundles the runtime inside your app, so the target needs nothing pre-installed — larger output, but fully portable and version-pinned. Modern .NET also adds single-file, trimming, and Native AOT on top. Framework had essentially only the "runtime must already be installed" model.
Q7What does NOT port when migrating a Framework app to modern .NET?
AThe Framework-only technologies: Web Forms, server-side WCF hosting, Windows Workflow Foundation, AppDomains, and .NET Remoting. Most business logic, EF, LINQ, and common APIs port cleanly. The unportable pieces must be re-architected — Web Forms to Razor/Blazor, WCF to gRPC or Web API, WF to a message-driven design, AppDomains to separate processes. The sensible approach is incremental migration using the strangler-fig pattern rather than a big-bang rewrite.
Q8Should every app be migrated to modern .NET?
AFor any new project, yes — modern .NET is faster, cross-platform, and where all investment goes. But an existing, stable Framework app that depends heavily on Framework-only tech may not be worth the migration cost, especially if it changes rarely. The mature position is that the decision is a cost/benefit trade-off, not a reflex — and knowing when not to migrate is itself a sign of judgement.

One-liner: Framework = old Windows-only 2002 engine (frozen at 4.8). Core = modern, cross-platform, open-source rewrite. Both run C#; they're siblings, not versions.
Naming: Core 1.0→3.1, then renamed (skipping "4") to .NET 5 → 6 → 8 (LTS). ".NET 8" is modern Core, NOT Framework 4.8.
Why Core exists: Linux/cloud/containers, no DLL hell (side-by-side), not IIS-bound, modular, faster, annual releases.
Architecture: Framework = CLR + GAC + machine-wide. Core = CoreCLR + RyuJIT + app-local NuGet, no GAC.
Deployment: Framework-dependent (small, needs runtime) vs Self-contained (bundles runtime, runs anywhere). Plus single-file, trimming, AOT.
TFM: net8.0 = modern, net48 = Framework, netstandard2.0 = shared contract for both worlds.
Won't port: Web Forms, server-side WCF, Windows Workflow Foundation, AppDomains, .NET Remoting.
Migration: incremental, strangler-fig pattern, .NET Upgrade Assistant, .NET Standard as the bridge. Know when NOT to migrate.
