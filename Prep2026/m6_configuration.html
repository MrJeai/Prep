Week 1 — Module 6 · Configuration

Configuration & Environments

Coming from web.config, this is one of the biggest "the new way is genuinely better" moments. ASP.NET Core has a layered configuration system that reads from many sources, binds to typed classes, and switches behaviour per environment — all without recompiling. This module covers how it works, the precedence rules interviewers ask about, and how to handle secrets safely.

Interview ROI: Medium
Real-world: Essential
Week 1 · Phase 1
01

Why Config Exists

From rigid web.config XML to a flexible layered model

Configuration is any setting your app needs but that shouldn't be hard-coded: connection strings, API keys, feature flags, log levels, external URLs. The cardinal rule is the same compiled build must run in dev, test, and production — only the configuration changes. Hard-coding these values breaks that rule.

1.1 — The old way vs the new way
.NET FrameworkASP.NET Core
Single web.config XML fileMany sources merged into one model
XML, verbose, error-proneJSON, env vars, secrets, command line
Read via ConfigurationManager.AppSettings[...]Injected IConfiguration or typed IOptions<T>
Environment switching was awkward (transforms)Built-in per-environment files & precedence
📖 Definition — Configuration provider
A configuration provider is a source of key-value settings. ASP.NET Core reads from several providers and merges them into a single IConfiguration object, where later providers override earlier ones with the same key. This layering is the heart of the system.
02

Providers & Precedence

Which source wins when the same key appears twice

CreateBuilder registers the default providers in a specific order. Each later provider overrides the same key from earlier ones — this is the rule interviewers love to test.

1
appsettings.json
Base settings, committed to source control. Lowest priority.
↓ overridden by
2
appsettings.{Environment}.json
e.g. appsettings.Development.json — overrides the base for that environment.
↓ overridden by
3
User Secrets (Development only)
Local secrets kept outside the project folder.
↓ overridden by
4
Environment variables
How production/containers usually inject settings & secrets.
↓ overridden by
5
Command-line arguments
Highest priority — wins over everything.
⚠️ Remember the direction
Lowest → highest: appsettings → environment file → user secrets → env vars → command line. So an environment variable always beats the value in appsettings.json — which is exactly how you override the production connection string without touching the file.
03

Reading Configuration

Direct access vs the strongly-typed options pattern
3.1 — A sample appsettings.json
JSONappsettings.json
{
  "ConnectionStrings": {
    "Default": "Server=.;Database=TaskDb;Trusted_Connection=True;"
  },
  "Jwt": {
    "Issuer": "taskapi",
    "ExpiryMinutes": 60
  }
}
3.2 — Direct access via IConfiguration

Inject IConfiguration and read by key (use : to navigate sections):

C#
var conn = _config.GetConnectionString("Default");
var issuer = _config["Jwt:Issuer"];
var expiry = _config.GetValue<int>("Jwt:ExpiryMinutes");
📝 Fine for one-off reads, not great everywhere
Reading by magic string is error-prone (typos, no type safety). For anything used in more than one place, prefer the options pattern below.
3.3 — The options pattern (recommended)

Bind a config section to a typed class and inject it. This gives compile-time safety and clean, testable code.

C#
// 1) A class mirroring the section
public class JwtSettings
{
    public string Issuer { get; set; }
    public int ExpiryMinutes { get; set; }
}

// 2) Bind it in Program.cs
builder.Services.Configure<JwtSettings>(
    builder.Configuration.GetSection("Jwt"));

// 3) Inject it anywhere
public TokenService(IOptions<JwtSettings> options)
{
    _settings = options.Value;
}
💡 IOptions vs IOptionsSnapshot vs IOptionsMonitor
IOptions<T> — singleton, value fixed at startup (most common). IOptionsSnapshot<T> — scoped, re-read per request (picks up file changes). IOptionsMonitor<T> — singleton with live change notifications. Know that all three exist; reach for plain IOptions by default.
04

Environments

One build, different behaviour per environment

ASP.NET Core reads an environment variable, ASPNETCORE_ENVIRONMENT, to decide which environment it's running in. The three conventional values are Development, Staging, and Production (you can add your own).

C#
if (app.Environment.IsDevelopment())
{
    app.UseSwagger();         // expose API docs only in dev
    app.UseSwaggerUI();
}
else
{
    app.UseExceptionHandler("/error");  // hide stack traces in prod
    app.UseHsts();
}
📝 How it ties together
Two things key off the environment: (1) the matching appsettings.{Environment}.json file is loaded and overrides the base, and (2) your code can branch on app.Environment.IsDevelopment() to change behaviour — e.g. show detailed errors and Swagger in Development, but a generic error page and HSTS in Production. Same code, different runtime behaviour, driven entirely by one env var.
05

Secrets Management

Where credentials go — and where they must never go
🚫 The #1 rule
Never commit secrets (connection strings with passwords, API keys, JWT signing keys) to source control in appsettings.json. They end up in Git history forever. This is both a security failure and an interview red flag.
🧑‍💻
Development
Use User Secrets (dotnet user-secrets set ...) — stored outside the project folder, so they're never committed.
🚀
Production
Use environment variables (injected by the host/container) or a secret store like Azure Key Vault.
📄
appsettings.json
Only non-secret defaults and structure. The real secret is layered on top by a higher-priority provider.
💡 It just works because of precedence
Because env vars and Key Vault sit above appsettings.json in precedence, your code reads GetConnectionString("Default") the same way everywhere — the secret value simply comes from a safe source in production and from user secrets in dev. The reading code never changes.
06

Interview Preparation

Questions and model answers at the 4 YOE level
Q1How does configuration work in ASP.NET Core?
AIt reads key-value settings from multiple providers — appsettings.json, the environment-specific appsettings file, user secrets, environment variables, and command-line args — and merges them into a single IConfiguration. Later providers override earlier ones for the same key. You read values directly via IConfiguration or, preferably, bind sections to typed classes and inject them with IOptions.
Q2What's the precedence order, and why does it matter?
AFrom lowest to highest: appsettings.json, appsettings.{Environment}.json, user secrets, environment variables, command line. It matters because it lets you ship one build and override settings per environment without recompiling — for example, a production environment variable overrides the connection string in appsettings.json.
Q3What is the options pattern?
ABinding a configuration section to a strongly-typed POCO and injecting it via IOptions<T>. It gives type safety, avoids magic-string keys scattered around the code, and is easy to unit test. You register it with Services.Configure<T>(Configuration.GetSection("...")).
Q4How do you manage secrets safely?
ANever commit them. In development use User Secrets, which live outside the project. In production use environment variables or a managed secret store like Azure Key Vault. Because these providers have higher precedence than appsettings.json, the reading code is identical across environments — only the source of the value changes.
Q5How does the app know which environment it's in?
AFrom the ASPNETCORE_ENVIRONMENT variable — typically Development, Staging, or Production. It controls which appsettings.{Environment}.json file is loaded and lets code branch via app.Environment.IsDevelopment() to change behaviour, like enabling Swagger and detailed errors only in Development.
