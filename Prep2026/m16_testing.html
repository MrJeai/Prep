Why & Types of Tests

The test pyramid

Tests let you change code with confidence and catch regressions before users do. They come in layers — the test pyramid says have many fast unit tests, fewer integration tests, and very few slow end-to-end tests.

▿
Unit tests (most)
One class/method in isolation, dependencies mocked. Fast, numerous.
↓
▿
Integration tests (some)
Multiple components together, e.g. API + real/in-memory DB.
↓
▿
End-to-end (few)
Whole system through the UI/API. Slow, brittle — keep minimal.
02

xUnit Basics

Facts, Theories, and the AAA structure

xUnit is the most common .NET test framework. A [Fact] is a single test; a [Theory] runs the same test with multiple inputs via [InlineData]. Structure every test as Arrange–Act–Assert (AAA).

C#DiscountServiceTests.cs
[Fact]
public void Premium_customer_gets_10pct()
{
    // Arrange
    var sut = new DiscountService();
    // Act
    var rate = sut.RateFor(CustomerType.Premium);
    // Assert
    Assert.Equal(0.1m, rate);
}

[Theory]
[InlineData(2, 3, 5)]
[InlineData(-1, 1, 0)]
public void Adds(int a, int b, int expected)
    => Assert.Equal(expected, Calc.Add(a, b));
📝 "sut"
A common convention: sut = "system under test", the thing you're actually testing, to distinguish it from its collaborators.
03

Mocking with Moq

Isolating the class under test

A true unit test isolates one class — so its dependencies (a repository, an email sender) are replaced with mocks: fake implementations you control. Moq is the popular .NET mocking library. This is exactly why you depend on interfaces via DI (Module 5) — you can swap the real implementation for a mock.

C#
var repo = new Mock<IOrderRepo>();
repo.Setup(r => r.GetByIdAsync(1))
    .ReturnsAsync(new Order { Id = 1 });

var sut = new OrderService(repo.Object);  // inject the mock
var result = await sut.GetAsync(1);

repo.Verify(r => r.GetByIdAsync(1), Times.Once);
📖 Stub vs mock
A stub just returns canned data so the test can run. A mock also lets you verify interactions (was this method called once?). Moq does both.
04

Integration Testing

Testing the API end-to-end in-process

Integration tests exercise several layers together — the real pipeline, routing, model binding, and often a database. ASP.NET Core provides WebApplicationFactory<T>, which spins up your app in-memory so you can send real HTTP requests to it without a network.

C#
var client = _factory.CreateClient();
var res = await client.GetAsync("/api/tasks/1");
Assert.Equal(HttpStatusCode.OK, res.StatusCode);
💡 Test database options
For the DB layer you can use a real test database (most faithful), a containerised one, or the EF Core in-memory provider (fast but doesn't enforce relational constraints). Knowing the trade-off — fidelity vs speed — is the interview-worthy point.
05

Best Practices

Tests that help instead of hurt
  • ✓Test behaviour, not implementation — assert on outcomes, so refactors don't break tests needlessly.
  • ✓Descriptive names — Method_Scenario_ExpectedResult reads like a spec.
  • ✓One logical assertion per test — a failure should point to one cause.
  • ✓Fast & independent — no shared state, no ordering dependency, no real network.
  • ✓Test the risky logic — business rules, edge cases, error paths — not trivial getters.
⚠️ Coverage is a guide, not a goal
100% coverage of trivial code proves little; thoughtful tests of the hard logic prove a lot. If asked about coverage, say you target meaningful coverage of business logic rather than a vanity percentage.
06

Interview Preparation

Questions and model answers at the 4 YOE level
Q1Unit vs integration test?
AA unit test checks one class in isolation with its dependencies mocked — fast and numerous. An integration test exercises multiple components together, like the API pipeline with a real or in-memory database, to verify they work as a whole. The pyramid says favour many unit tests, fewer integration, very few end-to-end.
Q2Why do you mock dependencies?
ATo isolate the class under test so a failure points to that class, not a database or external service, and to keep tests fast and deterministic. It's possible precisely because we depend on interfaces via DI — I can inject a Moq mock in place of the real implementation and control or verify its behaviour.
Q3What does AAA mean and why use it?
AArrange–Act–Assert: set up the inputs and the system under test, perform the action, then assert the outcome. It keeps tests readable and makes the intent obvious, which matters since tests double as documentation.
Q4How do you integration-test an ASP.NET Core API?
AWith WebApplicationFactory, which hosts the app in-memory so I can send real HttpClient requests through the actual pipeline — routing, binding, filters — and assert on status codes and responses. For the database I choose between a real test DB for fidelity or the in-memory provider for speed.
Q5Is high code coverage the goal?
ANo — coverage is a guide, not a target. I aim for meaningful tests of business logic, edge cases, and error paths rather than chasing a percentage by testing trivial getters. Good tests assert behaviour so refactoring doesn't break them unnecessarily.
