Controllers, Routing, Model Binding, Validation & API Design

This is where requests turn into code you write. A request arrives, routing picks your method, model binding fills your parameters, validation checks them, your controller delegates to a service, and you return a typed response. This module covers each step thoroughly, plus the API-design rules that make the difference between a hobby API and a production one.

01

Controllers & Their Role

Thin by design — the traffic controller, not the engine
1.1 — What a controller is for

A controller is the entry point for HTTP requests into your application. Its job is narrow and it should stay that way. A controller should: (1) accept the request, (2) let model binding + validation handle the input, (3) call a service to do the actual work, and (4) return an appropriate HTTP response. That's it.

❌
Controllers should NOT contain
Business logic, database queries, complex calculations, or orchestration of multiple steps.
→ All of that belongs in the service layer.
✅
The correct flow
Controller → Service → Repository → Database. Each layer has one responsibility.
→ Thin controllers are testable, reusable, and easy to read.
💡 Why "thin controllers" is a quality signal
Interviewers use this to gauge maturity. Fat controllers (business logic stuffed into the action) are untestable and unmaintainable. Keeping logic in services means you can unit-test the logic without spinning up HTTP, and reuse it across multiple endpoints.
1.2 — ControllerBase, [ApiController], and a first example
C#TasksController.cs
[ApiController]
[Route("api/[controller]")]
public class TasksController : ControllerBase
{
    private readonly ITaskService _service;
    public TasksController(ITaskService service) => _service = service;

    [HttpGet("{id:int}")]
    public async Task<ActionResult<TaskDto>> GetById(int id)
    {
        var task = await _service.GetByIdAsync(id);
        return task is null ? NotFound() : Ok(task);
    }
}
ElementWhat it does
ControllerBaseBase class for API controllers — gives helpers like Ok(), NotFound(). (Use Controller only if you also render Views.)
[ApiController]Opts into API conventions: automatic 400 on invalid input, binding-source inference, attribute-routing requirement.
[Route("api/[controller]")]Sets the base URL; [controller] token → the class name minus "Controller" (→ tasks).
02

Routing

How a URL is matched to your method
2.1 — Attribute routing (the API standard)

Routing is the process of matching an incoming URL + HTTP method to a specific controller action. Modern APIs use attribute routing — you declare the route directly on the method with verb attributes:

AttributeHTTP verbExample route
[HttpGet]GET (read)GET /api/tasks
[HttpGet("{id}")]GET oneGET /api/tasks/5
[HttpPost]POST (create)POST /api/tasks
[HttpPut("{id}")]PUT (replace)PUT /api/tasks/5
[HttpDelete("{id}")]DELETEDELETE /api/tasks/5
2.2 — Route constraints

You can constrain a route parameter's type or shape. This prevents bad matches and avoids needless work:

C#
[HttpGet("{id:int}")]      // only matches integers
[HttpGet("{id:guid}")]     // only matches GUIDs
[HttpGet("{slug:minlength(3)}")] // at least 3 chars
📝 How routing fits the pipeline
Routing runs as middleware: UseRouting matches the endpoint early, then authorization can act on it, and MapControllers executes the matched action at the end. So by the time your method runs, the framework already knows it's the right one and has the route values ready for binding.
03

Model Binding

Turning raw HTTP data into C# objects

Model binding is the framework feature that automatically reads data from the request (the JSON body, route, query string, headers) and maps it onto your action's parameters — converting strings into int, DateTime, your DTO classes, and so on. You almost never parse the raw request yourself.

SourceAttributeUsed for
Request body (JSON)[FromBody]POST/PUT payloads → a DTO
Query string[FromQuery]?page=2&sort=name
Route segment[FromRoute]The {id} in the URL
HTTP header[FromHeader]Custom headers, correlation IDs
Form fields[FromForm]File uploads, form posts
C#
[HttpPost]
public async Task<IActionResult> Create([FromBody] CreateTaskDto dto)
{
    // ASP.NET read the JSON, built a CreateTaskDto, validated types — all automatically
    var created = await _service.CreateAsync(dto);
    return CreatedAtAction(nameof(GetById), new { id = created.Id }, created);
}
💡 [ApiController] infers the source
With [ApiController], you usually don't need the attributes: complex types are assumed to come [FromBody], and simple types from the route/query. Knowing the explicit attributes still matters for interviews and edge cases.
04

Validation

Rejecting bad input before it reaches your logic
4.1 — Data annotations + automatic 400

Decorate your DTO with validation attributes. After binding, the framework checks them and populates ModelState. With [ApiController], an invalid model automatically returns a 400 Bad Request with a structured error body — you don't write any checking code.

C#CreateTaskDto.cs
public class CreateTaskDto
{
    [Required]
    [MaxLength(100)]
    public string Title { get; set; }

    [Range(1, 5)]
    public int Priority { get; set; }
}
📖 The validation flow
Request received → model binding maps it → validation attributes evaluated → ModelState filled. If invalid and [ApiController] is present, a 400 with ProblemDetails is returned automatically, before your action body runs. So your controller can safely assume the input is structurally valid.
4.2 — Custom & complex validation

Common annotations: [Required], [StringLength], [Range], [EmailAddress], [RegularExpression]. For rules spanning multiple fields or needing services, implement IValidatableObject or use FluentValidation — a popular library that expresses rules in clean, testable C# instead of attributes (covered more in the Clean Architecture module).

05

Return Types & Responses

Returning the right status code, the typed way
5.1 — IActionResult vs ActionResult<T>
Return typeWhen to use
IActionResultYou only return status results (Ok, NotFound) and don't need a typed payload signature.
ActionResult<T>Preferred. Lets you return either a T (the data) or a status result, and documents the response type for Swagger/OpenAPI.

Use the built-in helpers to return correct status codes — they read clearly and set everything for you:

C#
Ok(data)                // 200
CreatedAtAction(...)      // 201 + Location header
NoContent()             // 204 (after a successful delete)
BadRequest(errors)       // 400
NotFound()              // 404
Conflict()              // 409
📝 ProblemDetails — standardised errors
ASP.NET Core returns errors in the ProblemDetails format (RFC 7807) — a consistent JSON shape with type, title, status, and detail. Using it everywhere means clients can handle all your errors uniformly. Pair it with a global exception-handling middleware (your Middleware module) so even unhandled errors come back in this shape.
06

API Design Best Practices

The rules that make an API production-grade
6.1 — Always use DTOs, never expose entities

Return and accept DTOs (Data Transfer Objects), not your EF Core entities. Entities are your database shape; DTOs are your API contract. Mixing them leaks internal structure, creates security risks (over-posting), and tightly couples your API to your schema.

🛡️
Security
A DTO can't be over-posted — a client can't sneak in IsAdmin=true if it's not on the DTO.
🔗
Decoupling
Change the database without breaking the API contract, and vice versa.
🎯
Shape control
Return exactly the fields the client needs — no lazy-loaded graphs or sensitive columns.
6.2 — Pagination, filtering, sorting

Never return an unbounded collection. Accept paging in the query string and return a page plus metadata:

HTTP
GET /api/tasks?status=open&sort=createdAt&order=desc&page=1&pageSize=20
6.3 — Versioning & idempotency

Versioning protects existing clients from breaking changes — commonly /api/v1/.... Idempotency matters for safe retries: PUT/DELETE are naturally idempotent, and for POST you can accept an idempotency key header so a retried request doesn't create duplicates. (Full HTTP/REST grounding is in Module 1.)

💡 The product-company checklist
DTOs everywhere · correct status codes · ProblemDetails errors · pagination on all collections · versioning from day one · validation at the edge · thin controllers. Hit these and your API reads as senior work.

Interview Preparation

Questions and model answers at the 4 YOE level
Q1Why should controllers be thin?
ABecause a controller's only job is HTTP concerns — accept the request, rely on binding/validation, call a service, and return a response. Putting business logic in the controller makes it untestable (you'd need HTTP to test logic) and unreusable. Keeping logic in services means it can be unit-tested in isolation and shared across endpoints.
Q2What does [ApiController] give you?
AIt opts into API conventions: automatic 400 responses when model validation fails, inference of binding sources (complex types from the body, simple types from route/query), a requirement for attribute routing, and ProblemDetails-formatted errors. It removes a lot of boilerplate you'd otherwise write.
Q3How does model binding work?
AAfter routing matches an action, the framework reads data from the request — the JSON body, route values, query string, headers — and maps it onto the action's parameters, converting types and constructing DTOs automatically. You control the source with attributes like [FromBody], [FromQuery], [FromRoute], though [ApiController] infers most of them.
Q4How does validation work and when does the 400 happen?
AYou annotate DTOs with attributes like [Required] and [Range]. After binding, the framework evaluates them and fills ModelState. With [ApiController], an invalid model automatically returns a 400 with a ProblemDetails body before your action runs, so the action can assume valid input. For complex rules, use IValidatableObject or FluentValidation.
Q5IActionResult vs ActionResult<T>?
AIActionResult only describes a result (Ok, NotFound) without a typed payload. ActionResult<T> lets the method return either the data T or a status result, and it documents the response type for Swagger/OpenAPI. ActionResult<T> is generally preferred for typed API actions.
Q6Why use DTOs instead of returning entities directly?
ADTOs decouple your API contract from your database schema, prevent over-posting (a client can't set fields you didn't expose), let you shape exactly the data the client needs, and avoid leaking sensitive columns or triggering lazy-loaded graphs. Entities are the persistence model; DTOs are the API model.
