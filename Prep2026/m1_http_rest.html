HTTP & REST Fundamentals

Every web API you build sits on top of two things: the HTTP protocol and the REST style. Most developers use them daily without truly understanding them — and it shows in interviews. This module builds that understanding from the ground up, so that when you're asked "what does idempotent mean?" or "why PUT not POST?", you answer with reasoning, not memorised trivia.

How the Web Talks

The client–server model and the request–response cycle
1.1 — What is HTTP, really?

HTTP (HyperText Transfer Protocol) is the language browsers, mobile apps, and servers use to talk to each other over the internet. It is a set of agreed-upon rules for how a client asks for something and how a server replies. When you build a Web API in ASP.NET Core, you are not inventing a way to communicate — you are speaking HTTP, the same protocol the entire web runs on.

Three properties define HTTP, and each one shapes how you design APIs:

📞
Request–Response
The client always speaks first by sending a request; the server answers with exactly one response. The server never initiates.
🧠
Stateless
Each request is independent. The server remembers nothing about previous requests unless you deliberately add state (cookies, tokens, a database).
📄
Text-based
HTTP messages are human-readable text (a start line, headers, and an optional body), which is why tools like Postman can show you exactly what's sent.
📖 Definition — Stateless
Stateless means the server treats every request as brand new and keeps no memory of the client between requests. If a request needs context (e.g. "who am I?"), the client must supply it every time — typically as a token in a header. This is the single most important property to understand, because it's why APIs send a JWT on every call rather than "logging in once" on the server.
1.2 — The journey of one request

When a client calls GET https://api.shop.com/products/42, here is the full round trip:

1
Client builds an HTTP request
Method (GET), URL, headers, optional body.
↓
2
DNS resolves the domain → IP, TCP/TLS connection opens
HTTPS adds a TLS handshake that encrypts everything.
↓
3
Server receives & processes
Your ASP.NET Core app runs: middleware → routing → controller → DB.
↓
4
Server returns one HTTP response
Status code, headers, body (usually JSON).
↓
5
Client reads the response & the cycle ends
Connection may stay open (keep-alive) for reuse, but this exchange is complete.

Anatomy of a Request & Response

The exact parts of each message — what every byte means
2.1 — A raw HTTP request

An HTTP request has four parts: a start line (method + path + version), headers, a blank line, and an optional body. Here is a real POST request:

HTTPrequest
POST /api/products HTTP/1.1          ← start line: method, path, version
Host: api.shop.com                 ← headers (metadata)
Authorization: Bearer eyJhbGciOi...   ← who you are (a JWT)
Content-Type: application/json       ← format of the body
Accept: application/json             ← format you want back
                                       ← blank line separates headers from body
{ "name": "Keyboard", "price": 1200 }   ← body (payload)
PartWhat it isExample
MethodThe action you want (verb)GET, POST
Path / URLWhich resource/api/products/42
HeadersMetadata about the requestContent-Type, Authorization
BodyThe payload (data you send)JSON for POST/PUT
2.2 — A raw HTTP response
HTTPresponse
HTTP/1.1 201 Created          ← status line: version, code, reason
Content-Type: application/json
Location: /api/products/42        ← where the new resource lives

{ "id": 42, "name": "Keyboard", "price": 1200 }
📝 Headers worth knowing by name
Content-Type (the format of this message's body), Accept (the format the client wants back), Authorization (credentials, usually a Bearer token), Cache-Control (caching rules), and Location (URL of a newly created resource). Interviewers often ask the difference between Content-Type and Accept — one describes what you're sending, the other what you'd like to receive.

HTTP Methods & Status Codes

Verbs, response codes, and the all-important idempotency
3.1 — The methods (verbs)

The HTTP method tells the server what kind of action the client wants on a resource. Choosing the right one is the heart of good API design.

MethodPurposeHas body?Safe?Idempotent?
GETRead a resourceNo✅ Yes✅ Yes
POSTCreate a new resourceYes❌ No❌ No
PUTReplace a resource fullyYes❌ No✅ Yes
PATCHUpdate part of a resourceYes❌ No⚠️ Usually not
DELETERemove a resourceNo❌ No✅ Yes
📖 Definition — Safe vs Idempotent
Safe = the request doesn't change server state (a pure read). Idempotent = making the same request many times has the same effect as making it once. DELETE /products/42 is idempotent: delete it once or ten times, the end state is identical (it's gone). POST is not: call it three times and you create three products.
💡 Why this matters in the real world
Idempotency is what makes safe retries possible. If a network blip means the client never got the response, it can safely retry a PUT or DELETE without fear of duplicates. For POST, you protect against duplicates with an idempotency key (a unique header the server uses to detect repeats) — a favourite interview follow-up.
3.2 — Status codes

The status code is a three-digit number that tells the client what happened. The first digit defines the category:

ℹ️
1xx — Informational
Rare in APIs. Request received, continuing.
✅
2xx — Success
200 OK, 201 Created, 204 No Content (success, nothing to return).
↪️
3xx — Redirection
301 Moved Permanently, 304 Not Modified (use your cache).
🙋
4xx — Client error
400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 429 Too Many Requests.
💥
5xx — Server error
500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable.
⚠️ The 401 vs 403 trap
401 Unauthorized actually means "unauthenticated" — we don't know who you are (missing/invalid token). 403 Forbidden means "we know who you are, but you're not allowed." Mixing these up is a classic interview slip.
04

REST Principles

What makes an API "RESTful" — the constraints that matter
4.1 — What REST is

REST (Representational State Transfer) is not a protocol or a library — it's an architectural style, a set of constraints for designing networked APIs, defined by Roy Fielding in 2000. An API that follows these constraints is called RESTful. The core idea is simple and powerful: model everything as a "resource", give each resource a URL, and act on it using standard HTTP methods.

📖 Definition — Resource
A resource is any "thing" your API exposes — a product, a user, an order. It's identified by a URL (e.g. /products/42) and represented in a format like JSON. You don't put verbs in the URL; the HTTP method is the verb. So it's DELETE /products/42, never /deleteProduct?id=42.
4.2 — The key REST constraints
  • ▸Client–Server: the client (UI) and server (data/logic) are separate and evolve independently.
  • ▸Stateless: every request carries everything the server needs; the server stores no client session between calls. This is what lets you scale to many servers behind a load balancer.
  • ▸Uniform Interface: resources are addressed by URLs and manipulated with the standard methods — consistency makes APIs predictable.
  • ▸Cacheable: responses say whether they can be cached, improving performance.
  • ▸Layered System: the client can't tell if it's talking to the real server or a proxy/load balancer/gateway in between.
📝 Statelessness — the constraint interviewers probe
Because REST is stateless, scaling out is easy: any server can handle any request, since no server holds session data. This is exactly why authentication uses a JWT sent on every request rather than a server-side session — it keeps the API stateless and horizontally scalable. Connect these dots out loud and you sound senior.
4.3 — Richardson Maturity Model (nice to mention)

A handy way to describe "how RESTful" an API is, in four levels: L0 — one URL, everything over POST (basically RPC); L1 — multiple resource URLs but still mostly POST; L2 — proper use of HTTP methods and status codes (where most good real-world APIs live); L3 — adds HATEOAS (responses include links to related actions). You don't need L3 in practice, but naming this model signals depth.

Designing RESTful APIs

Practical rules you'll apply in every project and defend in interviews
5.1 — Resource naming

Good URLs are nouns, plural, lowercase, and hierarchical. Let the method express the action.

❌ Avoid✅ PreferWhy
GET /getAllProductsGET /productsThe verb is the HTTP method, not the URL.
POST /createProductPOST /productsPOST to the collection means "create".
GET /product/42GET /products/42Use plural collections consistently.
GET /products/42/getReviewsGET /products/42/reviewsNest sub-resources by hierarchy.
5.2 — Filtering, sorting, pagination

These belong in the query string, not the path, because they shape a collection rather than identify a resource:

HTTP
GET /products?category=electronics&sort=price&order=desc&page=2&pageSize=20
💡 Always paginate collections
Returning every row of a large table in one response is a real-world performance disaster (and a red flag in interviews). Default to a sensible pageSize, return the total count or paging metadata, and never let a client request "everything".
5.3 — Versioning

APIs evolve, but existing clients must not break. So you version. The two common approaches:

URL versioning
/api/v1/products
  • Simple, visible, easy to route.
  • Most common in practice.
Header versioning
api-version: 1.0
  • Cleaner URLs.
  • Harder to test/discover.
5.4 — Use the right status codes & consistent errors

Return 201 Created with a Location header on creation, 204 No Content on a successful delete, 400 for validation errors, 404 when a resource doesn't exist, 409 for conflicts. ASP.NET Core ships a standard error format called ProblemDetails (RFC 7807) — use it so every error in your API looks the same.

06

Interview Preparation

Questions and model answers at the 4 YOE level
Q1What does it mean that HTTP is stateless, and why does it matter?
AStateless means the server keeps no memory of a client between requests — each request must carry all the context it needs. It matters because it makes APIs horizontally scalable: any server behind a load balancer can handle any request, since none of them hold session state. It's also why authentication sends a token on every request instead of relying on a server-side session.
Q2What's the difference between PUT and PATCH?
APUT replaces the entire resource with the payload you send — omit a field and it's effectively cleared. PATCH applies a partial update, changing only the fields you provide. PUT is idempotent; PATCH usually isn't, depending on the operation.
Q3Explain idempotency and give an example.
AAn operation is idempotent if performing it multiple times has the same effect as performing it once. DELETE /orders/5 is idempotent — after the first call the order is gone, and repeats leave it gone. POST /orders is not — three calls create three orders. Idempotency lets clients safely retry after network failures; for POST you add an idempotency key to dedupe.
Q4401 vs 403?
A401 Unauthorized means you're not authenticated — we don't know who you are, usually a missing or invalid token. 403 Forbidden means you're authenticated but lack permission for this resource.
Q5Is REST the same as HTTP?
ANo. HTTP is the transport protocol. REST is an architectural style — a set of constraints (stateless, uniform interface, resources via URLs, standard methods) for designing APIs. REST is almost always implemented over HTTP, but they're different layers: you can violate REST while still using HTTP perfectly.
Q6How do you handle API versioning and why?
ABecause existing clients must keep working when the API changes, you version it — commonly via the URL (/api/v1/...) for visibility and easy routing, or via a header for cleaner URLs. You introduce a new version only for breaking changes; additive, backward-compatible changes don't need one.
