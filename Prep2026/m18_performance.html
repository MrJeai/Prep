Where APIs Get Slow

Measure before you optimise

The cardinal rule: measure first. Most API slowness comes from a handful of usual suspects, and the biggest wins are usually at the data layer, not micro-optimisations.

  • ✓Database — N+1 queries, missing indexes, loading too much (Modules 10 & 11). Usually the #1 cause.
  • ✓Blocking threads — sync-over-async starving the thread pool (Module 9).
  • ✓Repeated work — recomputing what could be cached (Module 17).
  • ✓Oversized payloads — returning everything, no pagination or compression.
💡 The senior framing
"I profile to find the bottleneck rather than guessing. In practice it's usually the database — N+1 or a missing index — so I start there before reaching for caching or compression."
02

Response Caching & Compression

Two cheap, high-impact middlewares
2.1 — Response caching

Whereas Module 17 caches data inside your app, response caching caches the whole HTTP response using Cache-Control headers, so clients and proxies can reuse it without hitting your server at all. Great for responses that are identical for everyone and change infrequently.

2.2 — Response compression

Compressing responses (Gzip/Brotli) shrinks payloads over the wire, cutting transfer time — especially for large JSON. Enable the middleware and the client negotiates it via Accept-Encoding.

C#
builder.Services.AddResponseCompression();
// ...
app.UseResponseCompression();
📝 Often handled at the edge
In many production setups the reverse proxy (Nginx) or a CDN does compression and response caching, taking that load off your app (ties to Module 3's reverse-proxy discussion).
03

Rate Limiting

Protecting the API from abuse and overload

Rate limiting caps how many requests a client can make in a time window, protecting against abuse, runaway clients, and accidental overload. When exceeded, the API returns 429 Too Many Requests. ASP.NET Core 8 has built-in rate-limiting middleware.

AlgorithmHow it worksNote
Fixed windowN requests per fixed interval (e.g. 100/min)Simple; allows bursts at window edges
Sliding windowCounts over a rolling intervalSmoother, fairer than fixed
Token bucketTokens refill at a rate; each request spends oneAllows controlled bursts
ConcurrencyCaps simultaneous in-flight requestsProtects a scarce resource
⚠️ Distributed rate limiting
Like in-memory caching, an in-process limiter doesn't coordinate across multiple instances. For a true global limit across a scaled-out app, the counter must live in a shared store (often Redis) — the same multi-instance lesson from Module 17.
04

Versioning & Pagination

Evolving and bounding your API (recap + depth)

Both were introduced in Module 8; here's the consolidated view. Versioning lets the API change without breaking existing clients — only for breaking changes. Pagination bounds response size so collections never return unbounded rows.

Versioning styleExampleTrade-off
URL/api/v1/ordersVisible, easy to route — most common
Query string/api/orders?api-version=1.0Simple, clutters URLs
Headerapi-version: 1.0Clean URLs, harder to discover/test
💡 Pagination styles
Offset (page/pageSize → SQL Skip/Take) is simple but drifts if rows are inserted mid-paging and gets slow at deep offsets. Cursor/keyset (give me items after this id) is stable and fast for large datasets. Mention both and you stand out.

Other Quick Wins

Cheap improvements with outsized impact
  • ✓Async all the way — frees threads under load (Module 9).
  • ✓Connection pooling — reuse DB connections instead of opening new ones; on by default in ADO.NET/EF, just don't defeat it.
  • ✓Fix N+1 & project with Select — fetch only needed columns (Module 10).
  • ✓AsNoTracking for read-only queries (Module 10).
  • ✓Cache hot reads (Module 17) and paginate (above).
📖 Connection pooling
Opening a database connection is expensive. A pool keeps a set of open connections and hands them out on demand, returning them when done — turning a costly setup into a cheap checkout. It's automatic; the mistake is accidentally disabling it or leaking connections by not disposing.

Interview Preparation

Questions and model answers at the 4 YOE level
Q1An API endpoint is slow. How do you approach it?
AMeasure first to find the bottleneck rather than guessing. Most often it's the database — an N+1 query or a missing index — so I check the queries and execution plan. Then I consider caching hot reads, ensuring async I/O so threads aren't blocked, projecting only needed columns, paginating, and compressing large payloads.
Q2What is rate limiting and which algorithms do you know?
AIt caps requests per client per time window to prevent abuse and overload, returning 429 when exceeded. Common algorithms: fixed window (simple, allows edge bursts), sliding window (smoother), token bucket (allows controlled bursts via refilling tokens), and concurrency limits. ASP.NET Core 8 has built-in middleware for these.
Q3Response caching vs the caching from the Redis module?
ARedis/data caching stores computed data inside the app so a handler can skip recomputation. Response caching caches the whole HTTP response via Cache-Control so clients, proxies, or CDNs can reuse it without hitting the server at all. They operate at different layers and complement each other.
Q4Offset vs cursor pagination?
AOffset uses page/pageSize translated to Skip/Take — simple but it can skip or repeat rows if data changes mid-paging and gets slow at deep offsets. Cursor (keyset) pagination returns items after a given key, which is stable under inserts and efficient on large datasets, at the cost of not jumping to arbitrary pages.
Q5How does rate limiting work across multiple instances?
AAn in-process limiter only counts per instance, so behind a load balancer the effective limit multiplies. For a true global limit the counter must live in a shared store like Redis so all instances coordinate — the same multi-instance consideration as distributed caching.
