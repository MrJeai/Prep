Logging & Monitoring in Production

Code that ships is code you have to operate. When something breaks at 2 a.m., observability is the difference between a five-minute fix and a three-hour outage. This module builds on Module 7's logging basics into production practice: structured logs with Serilog, correlation IDs and tracing across services, health checks, and the metrics-and-alerting mindset.

01

Observability

The three pillars

Observability is how well you can understand what's happening inside a running system from the outside. It rests on three pillars:

📜
Logs
Discrete, timestamped event records. "What happened, and when?" Great for debugging specifics.
📊
Metrics
Numeric measurements over time (request rate, latency, error %, CPU). "How is the system trending?"
🧵
Traces
The path of one request across components. "Where did the time/failure go?"
📖 Monitoring vs observability
Monitoring watches known signals and alerts on them ("CPU > 90%"). Observability is the broader capability to ask new questions about unexpected problems without shipping new code. Monitoring is a subset of, and depends on, good observability.
02

Structured Logging & Serilog

Logs you can query, not just read

Module 7 introduced ILogger and structured logging; in production it becomes essential. Structured logs attach named properties to each entry (as JSON) instead of baking values into a string — so you can query them ("all errors for orderId 42") in a log platform.

C#
// ✅ structured — OrderId becomes a queryable field
_logger.LogInformation("Order {OrderId} shipped to {Region}", id, region);
// ❌ string interpolation — loses structure, just text
_logger.LogInformation($"Order {id} shipped");
📝 Serilog & sinks
Serilog is the popular structured-logging library for .NET. A sink is a destination for logs — console, file, Seq, Elasticsearch, Application Insights. You configure sinks once at startup; the same log call fans out to all of them. In production logs go to a central platform, never just a local file on an ephemeral container.
⚠️ Don't log secrets or PII
Passwords, tokens, full card numbers, and personal data must never hit logs. Use appropriate levels (Module 7), and remember logs are widely accessible inside a company.
03

Correlation IDs & Distributed Tracing

Following one request through many services

In a system with multiple services (Module 19), one user action triggers calls across several of them. A correlation ID — a unique id attached at the entry point and passed along every downstream call and log — lets you filter all logs for that single request, even across services.

📖 Distributed tracing
Distributed tracing generalises this: each request gets a trace id, and each step (service, DB call) is a timed "span". Tools like Application Insights or OpenTelemetry stitch the spans into a waterfall so you can see exactly where latency or failure occurred across the whole call chain.
💡 Built-in support
ASP.NET Core sets an Activity/trace id automatically, and OpenTelemetry is the vendor-neutral standard for exporting traces and metrics. Mentioning OpenTelemetry signals current knowledge.
04

Health Checks

Letting the platform know if the app is alive

A health check is an endpoint (e.g. /health) that reports whether the app and its dependencies are healthy. Load balancers and orchestrators (App Service, Kubernetes) poll it to decide whether to send traffic to an instance or restart it.

C#
builder.Services.AddHealthChecks()
    .AddSqlServer(conn)
    .AddRedis(redisConn);
app.MapHealthChecks("/health");
📝 Liveness vs readiness
Liveness = "is the process alive?" (restart if not). Readiness = "is it ready to serve, with its dependencies available?" (hold traffic until yes). Splitting them prevents traffic hitting an instance that's started but not yet connected to its database.
05

Metrics & Alerting

Knowing — and being told — when things go wrong

Collect key metrics, watch them on dashboards, and set alerts so you're notified before users complain. A useful starting framework is the RED method for request-driven services:

SignalMeaning
RateRequests per second
ErrorsFailed-request rate (e.g. 5xx)
DurationLatency, usually p95/p99 not just average
💡 Percentiles over averages
Averages hide pain: a 50 ms average can still mean the slowest 1% of users wait 5 seconds. Track p95/p99 latency to catch the experience of your worst-served requests. Saying this shows operational maturity.

Interview Preparation

Questions and model answers at the 4 YOE level
Q1What are the three pillars of observability?
ALogs — discrete event records of what happened; metrics — numeric measurements over time like rate, errors, and latency; and traces — the path of a single request across components. Together they let you understand a running system from the outside. Monitoring alerts on known signals; observability is the broader ability to investigate new, unexpected problems.
Q2What is structured logging and why use it?
AInstead of baking values into a message string, you log named properties so each field is queryable in a log platform — like filtering all logs for a specific order id. In .NET, ILogger supports it with message templates, and Serilog writes structured logs to sinks like Seq, Elasticsearch, or Application Insights. You configure sinks once and every log fans out to them.
Q3How do you trace a request across multiple services?
AWith a correlation or trace id created at the entry point and propagated to every downstream call and log, so I can filter all logs for one request across services. Distributed tracing extends this: each step is a timed span under a trace id, and tools like Application Insights or OpenTelemetry stitch them into a waterfall showing where latency or failure occurred.
Q4What are health checks and the liveness/readiness distinction?
AA health-check endpoint reports whether the app and its dependencies are healthy so load balancers and orchestrators can route or restart instances. Liveness asks whether the process is alive — restart if not; readiness asks whether it's ready to serve with dependencies available — hold traffic until yes. Splitting them stops traffic reaching an instance that's started but not yet connected to its database.
Q5Which metrics would you watch, and why percentiles?
AI'd track the RED signals — request rate, error rate, and duration — plus resource use. For latency I watch p95 and p99, not the average, because averages hide tail latency: a low average can still mean the worst 1% of users wait seconds. I'd alert on error rate and latency thresholds so I'm notified before users complain.
