01

Why Containers

Killing "works on my machine"

A container packages your app with everything it needs to run — runtime, libraries, config — into one portable unit that behaves identically on your laptop, a teammate's machine, CI, and production. It solves the classic "works on my machine" problem by making the environment part of the artifact.

📖 Container vs Virtual Machine
A VM virtualises hardware and runs a full guest OS — heavy (GBs), slow to start. A container shares the host OS kernel and isolates just the app — lightweight (MBs), starts in seconds. That efficiency is why you can pack many containers on one host and scale them quickly.
💡 Why interviewers care
Containers give environment parity (dev = prod), fast and consistent deployments, easy horizontal scaling, and clean isolation between services — exactly what the scaling and microservices modules assume.
02

Images vs Containers

Blueprint vs running instance
Image
A read-only template — your app + dependencies, built once. Like a class.
  • Built from a Dockerfile, stored in a registry (Docker Hub, ACR).
Container
A running instance of an image. Like an object.
  • You can run many containers from one image.
📝 Layers & caching
Images are built in layers, one per Dockerfile instruction. Unchanged layers are cached and reused, so builds are fast — which is why you copy and restore dependencies before copying source code: dependency layers stay cached when only your code changes.
03

Dockerfile & Multi-Stage Builds

A production-style .NET image

A Dockerfile is the recipe for an image. For .NET the best practice is a multi-stage build: use the big SDK image to compile, then copy only the published output into a small runtime image — so the final image is lean and doesn't ship the compiler.

Dockerfile
# --- build stage (has the SDK) ---
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY *.csproj .
RUN dotnet restore            # cached unless csproj changes
COPY . .
RUN dotnet publish -c Release -o /app

# --- runtime stage (small, no SDK) ---
FROM mcr.microsoft.com/dotnet/aspnet:8.0
WORKDIR /app
COPY --from=build /app .
EXPOSE 8080
ENTRYPOINT ["dotnet", "MyApi.dll"]
💡 Why two stages matter
The final image uses the slim aspnet runtime, not the multi-GB sdk — smaller images deploy faster, use less storage, and have a smaller attack surface. This is a favourite "do you actually use Docker" check.
04

Docker Compose

Running a whole stack with one command

Real apps aren't just the API — they need a database, a cache, maybe a broker. Docker Compose defines multiple containers in one YAML file and starts them together (docker compose up), on a shared network so they can reach each other by service name.

YAMLdocker-compose.yml
services:
  api:
    build: .
    ports: ["8080:8080"]
    environment:
      - ConnectionStrings__Default=Server=db;...
    depends_on: [db, cache]
  db:
    image: mcr.microsoft.com/mssql/server:2022-latest
    environment: { ACCEPT_EULA: "Y", SA_PASSWORD: "Your_pwd1" }
  cache:
    image: redis:7
📝 Service discovery for free
Inside the Compose network the API reaches SQL Server at host db and Redis at cache — the service names become hostnames. That's why the connection string says Server=db, ties straight to config (Module 6).

Commands & Concepts

The vocabulary you'll be asked about
ConceptWhat it is
docker build -t app .Build an image from the Dockerfile
docker run -p 8080:8080 appRun a container, mapping host:container ports
Port mapping-p host:container exposes a container port to the host
VolumePersistent storage that outlives the container (e.g. DB data)
Environment variablesInject config/secrets at runtime (Module 6)
NetworkLets containers communicate by name
RegistryWhere images are stored/shared (Docker Hub, Azure Container Registry)
⚠️ Containers are ephemeral
A container's filesystem is thrown away when it stops. Anything that must persist (database files, uploads) belongs in a volume or external storage — not inside the container. Stateless app + external state is the same principle from REST and caching.

Interview Preparation

Questions and model answers at the 4 YOE level
Q1What problem do containers solve, and how do they differ from VMs?
AThey package an app with its runtime and dependencies so it runs identically everywhere, eliminating "works on my machine." Unlike a VM, which virtualises hardware and runs a full guest OS (heavy, slow), a container shares the host kernel and isolates just the app — lightweight and fast to start, so you can pack many on a host and scale quickly.
Q2Image vs container?
AAn image is a read-only template — your app plus dependencies, built from a Dockerfile and stored in a registry. A container is a running instance of an image. Like a class and an object: you can run many containers from one image.
Q3What is a multi-stage build and why use it for .NET?
AYou build in one stage using the SDK image to compile and publish, then copy just the published output into a small runtime image. The final image ships the aspnet runtime, not the multi-GB SDK, so it's smaller, deploys faster, and has a smaller attack surface.
Q4What does Docker Compose do?
AIt defines and runs a multi-container app from one YAML file — for example my API plus SQL Server and Redis — starting them together on a shared network where they reach each other by service name. One docker compose up spins up the whole stack, which is great for local development and integration testing.
Q5How do you persist data if containers are ephemeral?
AA container's filesystem is discarded when it stops, so persistent data goes in a volume — storage managed by Docker that outlives the container — or in external managed storage. The app stays stateless and state lives outside it, the same principle as keeping session and cache state external.
