Why SQL Still Matters

The ORM hides it; the interview tests it

You already work with SQL Server, so the relational basics aren't new. What interviews probe is the next layer: why a query is slow, how an index changes things, and what isolation level your code runs under. EF Core generates SQL, but it can't make good schema or indexing decisions for you — that judgement is yours, and it's what gets tested.

📝 The logical order SQL runs in
SQL isn't executed top-to-bottom as written. The logical order is: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. This explains two classic gotchas: you can't use a SELECT alias in a WHERE (the WHERE runs first), and you filter rows with WHERE but filter groups with HAVING.

Joins

Combining rows across tables — the everyday skill
JoinReturns
INNER JOINOnly rows with a match in both tables.
LEFT JOINAll rows from the left table + matches from the right (NULLs where none).
RIGHT JOINAll rows from the right + matches from the left.
FULL OUTER JOINAll rows from both; NULLs where there's no match on either side.
CROSS JOINCartesian product — every left row paired with every right row.
SELF JOINA table joined to itself (e.g. employee → manager in the same table).
SQLleft join example
SELECT c.Name, o.Total
FROM Customers c
LEFT JOIN Orders o ON o.CustomerId = c.Id;
-- every customer, even those with no orders (Total = NULL)
💡 The interview favourite: "find customers with no orders"
A LEFT JOIN ... WHERE o.Id IS NULL returns exactly the left rows that had no match — a very common question. Know that this "anti-join" pattern is what LEFT JOIN + IS NULL achieves.
03

Indexes & Execution Plans

How databases find rows fast — and the cost
3.1 — The book-index analogy

An index is a separate, sorted structure (a B-tree) that lets the database jump straight to rows instead of scanning the whole table — exactly like the index at the back of a book versus reading every page.

Clustered index
Defines the physical order of the table's rows. One per table (usually the primary key). The data is the index's leaf level.
Non-clustered index
A separate structure with a copy of the key columns + a pointer back to the row. Many per table. Great for columns you filter/join on often.
📖 Seek vs Scan (what you look for in a plan)
An index seek navigates directly to the rows it needs — fast, what you want. An index/table scan reads everything — fine for small tables or when most rows match, but a red flag on a large table filtered to a few rows. Reading the execution plan (the database's chosen strategy) to spot scans where seeks were possible is a senior skill.
3.2 — Indexes aren't free
✅
Indexes speed up reads
Filtering, joining, and sorting on indexed columns get dramatically faster.
⚠️
…but slow down writes & cost space
Every INSERT/UPDATE/DELETE must also maintain every index, and each index takes storage.
→ Index the columns you actually filter/join on; don't index everything.
📝 Covering index
A covering index includes (via INCLUDE) all the columns a query needs, so the query is answered entirely from the index without touching the table — eliminating expensive "key lookups." Mentioning this signals real indexing knowledge.
04

Normalization

Organising tables to avoid redundancy and anomalies

Normalization is the process of structuring tables so each piece of data lives in exactly one place, eliminating redundancy and the update/insert/delete anomalies it causes. Three normal forms cover almost everything you'll be asked.

1NF
First Normal Form
Atomic values only — no repeating groups or comma-lists in a column; each row unique.
↓
2NF
Second Normal Form
1NF + every non-key column depends on the whole primary key (no partial dependency on part of a composite key).
↓
3NF
Third Normal Form
2NF + no transitive dependencies (non-key columns don't depend on other non-key columns).
💡 Denormalization is a deliberate trade-off
Normalization optimises for correctness and write efficiency but can require many joins to read. Denormalization intentionally duplicates data to make reads faster (fewer joins) — common in reporting and high-read systems. The interview-savvy answer: "normalize by default for integrity; denormalize selectively when read performance demands it, accepting the redundancy cost."

Transactions, ACID & Isolation

Correctness when many users hit the same data
5.1 — ACID
⚛️
Atomicity
All steps in a transaction succeed, or none do.
✅
Consistency
A transaction moves the DB from one valid state to another (constraints hold).
🔒
Isolation
Concurrent transactions don't corrupt each other's view of the data.
💾
Durability
Once committed, changes survive crashes.
5.2 — Isolation levels & the anomalies they prevent
LevelDirty readNon-repeatable readPhantom
Read UncommittedPossiblePossiblePossible
Read Committed (SQL Server default)PreventedPossiblePossible
Repeatable ReadPreventedPreventedPossible
SerializablePreventedPreventedPrevented
📖 The three read anomalies
Dirty read: you read another transaction's uncommitted change (which may be rolled back). Non-repeatable read: you read a row twice in one transaction and get different values because someone updated it between. Phantom read: you run the same query twice and new rows appear because someone inserted matching rows. Higher isolation prevents more anomalies but reduces concurrency.
5.3 — Deadlocks

A deadlock occurs when transaction A holds a lock B needs, while B holds a lock A needs — neither can proceed. SQL Server detects this and kills one as the "deadlock victim," rolling it back. You reduce deadlocks by accessing tables in a consistent order, keeping transactions short, and using appropriate indexes so locks are taken on fewer rows.

Query Patterns Interviewers Ask

The recurring puzzles — know these cold
6.1 — GROUP BY + HAVING
SQLcustomers with more than 5 orders
SELECT CustomerId, COUNT(*) AS Orders
FROM Orders
GROUP BY CustomerId
HAVING COUNT(*) > 5;   -- HAVING filters groups; WHERE filters rows
6.2 — Find duplicates
SQL
SELECT Email, COUNT(*) 
FROM Users 
GROUP BY Email 
HAVING COUNT(*) > 1;
6.3 — Nth highest (window functions)

The "second-highest salary" question. The clean, modern answer uses a window function:

SQL2nd highest salary per department
SELECT * FROM (
  SELECT Name, DeptId, Salary,
         DENSE_RANK() OVER (PARTITION BY DeptId ORDER BY Salary DESC) AS rnk
  FROM Employees
) t
WHERE rnk = 2;
📝 Window functions to know
ROW_NUMBER() (unique sequential number), RANK() (gaps after ties), DENSE_RANK() (no gaps after ties), all with OVER (PARTITION BY ... ORDER BY ...). They compute per-group rankings without collapsing rows like GROUP BY does — a frequent "wow" answer in interviews.
6.4 — Stored procedures (awareness)

A stored procedure is precompiled SQL stored in the database, called by name. Pros: can encapsulate logic and may reduce round-trips; cons: business logic in the DB is harder to version and test than in C#. Most modern .NET apps keep logic in services and let EF Core generate queries, using procs mainly for heavy set-based operations. Know the trade-off.

Interview Preparation

Questions and model answers at the 4 YOE level
Q1Difference between clustered and non-clustered indexes?
AA clustered index defines the physical order of the rows and there's only one per table — typically the primary key, with the data stored in its leaf level. A non-clustered index is a separate sorted structure holding the key columns plus a pointer back to the row; you can have many. Clustered is the table sorted; non-clustered is a lookup structure pointing into it.
Q2When does an index hurt rather than help?
AIndexes speed reads but every write must maintain them and they consume storage. On write-heavy tables, or columns you rarely filter on, extra indexes cost more than they save. So you index the columns you actually filter, join, or sort on — not everything.
Q3WHERE vs HAVING?
AWHERE filters individual rows before grouping; HAVING filters groups after GROUP BY, so HAVING is where you put conditions on aggregates like COUNT(*) > 5. This follows SQL's logical order: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY.
Q4Explain the normal forms.
A1NF: atomic values, no repeating groups. 2NF: 1NF plus every non-key column depends on the whole primary key (no partial dependency). 3NF: 2NF plus no transitive dependencies — non-key columns depend only on the key, not on other non-key columns. You normalize for integrity and denormalize selectively when reads demand fewer joins.
Q5What's the default isolation level and what does it prevent?
ASQL Server's default is Read Committed, which prevents dirty reads but still allows non-repeatable reads and phantoms. Higher levels — Repeatable Read and Serializable — prevent more anomalies at the cost of concurrency, by holding more locks for longer.
Q6What is a deadlock and how do you reduce them?
AA deadlock is two transactions each holding a lock the other needs, so neither can proceed; SQL Server detects it and rolls one back as the victim. You reduce them by accessing tables in a consistent order, keeping transactions short, and indexing well so fewer rows are locked.
Q7How would you find the second-highest salary?
AUse a window function: DENSE_RANK() OVER (ORDER BY Salary DESC) in a subquery, then filter WHERE rnk = 2. DENSE_RANK handles ties without leaving gaps. You can partition by department to get the second highest per group. A correlated subquery with MAX also works but window functions are cleaner.
