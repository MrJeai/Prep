01

What System Design Is

Requirements before architecture

System design is about making sensible trade-offs to meet requirements at scale. Always separate two kinds of requirements first:

✅
Functional
What the system does — "shorten a URL," "send a message." The features.
📈
Non-functional
The qualities — scalability, availability, latency, consistency, durability. This is where design lives.
📖 Key quality terms
Scalability: handle growth by adding resources. Availability: % of time the system is up (the "nines"). Latency: time for one request. Throughput: requests handled per second. Durability: data isn't lost. You'll trade these against each other constantly.
02

Scaling & Load Balancing

Adding capacity
Vertical (scale up)
Bigger machine — more CPU/RAM.
  • Simple, no code change.
  • Hard ceiling; single point of failure; costly.
Horizontal (scale out)
More machines behind a load balancer.
  • Near-limitless, fault tolerant.
  • Requires stateless apps + coordination.
📖 Load balancer
A load balancer distributes incoming requests across multiple server instances. Common strategies: round robin (rotate evenly), least connections (send to the least-busy server), and hashing (sticky routing by key). It also detects unhealthy instances (via health checks, Module 24) and stops routing to them. Horizontal scaling lives or dies on a load balancer plus stateless servers — the statelessness theme from Modules 1, 17, and 23.
03

Caching & CDN

Avoiding work at every layer

Caching (Module 17) reappears at system scale as a primary scaling lever — a cache layer (Redis) in front of the database absorbs the bulk of reads. Caches can sit at many layers: client, CDN, load balancer, application, and database.

📖 CDN
A Content Delivery Network caches static content (images, JS, video) on servers geographically close to users, cutting latency and offloading your origin. It's the first thing to reach for with global users and heavy static assets.
💡 Read-heavy vs write-heavy
State the read/write ratio early. Most systems are read-heavy, so caching and read replicas give huge wins. Write-heavy systems push you toward sharding, queues, and write-optimised stores. The ratio drives the design.
04

Database Scaling

Replication, sharding, and SQL vs NoSQL
4.1 — Replication

Replication keeps copies of the data on multiple nodes. A common setup is primary-replica: writes go to the primary, reads fan out to replicas — scaling reads and adding redundancy. Replicas lag slightly, so reads can be marginally stale (eventual consistency).

4.2 — Sharding (partitioning)

Sharding splits data across multiple databases by a shard key (e.g. user id), so each holds a subset — scaling writes and total storage beyond one machine. Cost: cross-shard queries and joins get hard, and a bad shard key creates "hot" shards.

4.3 — SQL vs NoSQL
SQL (relational)NoSQL
SchemaFixed, structuredFlexible
StrengthsACID, joins, complex queriesHorizontal scale, high write throughput
Use whenStrong consistency, relationshipsHuge scale, simple access patterns, varied data
💡 Don't default to NoSQL for "scale"
A well-indexed SQL database with read replicas and caching handles enormous load. Reach for NoSQL when access patterns are simple and write/scale demands genuinely exceed what a relational DB can do — and say why.
05

CAP Theorem & Messaging

The consistency trade-off, and decoupling at scale
📖 CAP theorem
In a distributed system you can have at most two of Consistency, Availability, and Partition tolerance. Networks will partition, so P is non-negotiable — meaning the real choice during a partition is C vs A: either reject requests to stay consistent (CP), or stay available and serve possibly-stale data (AP). Many large systems choose AP with eventual consistency.
Messaging & queues at scale

Message queues (Module 20) are a core scaling tool: they decouple producers from consumers and level load by absorbing spikes, so a burst of work is processed steadily rather than crushing a downstream service. Any "process this later / asynchronously / at high volume" requirement is a cue to introduce a queue.

💡 Estimation
Be ready to do quick back-of-envelope math: from "1M daily active users" estimate requests/sec, storage/day, and bandwidth. Interviewers want a reasonable ballpark and clear assumptions, not precision.

Interview Preparation

Questions and model answers at the 4 YOE level
Q1Vertical vs horizontal scaling?
AVertical means a bigger machine — simple but capped, costly, and a single point of failure. Horizontal means more machines behind a load balancer — near-limitless and fault tolerant, but it requires stateless apps so any instance can serve any request, with shared state in something like Redis. Most large systems scale horizontally.
Q2How does a load balancer work and what strategies exist?
AIt distributes requests across instances and routes around unhealthy ones using health checks. Common strategies are round robin, least connections, and key-based hashing for sticky routing. It's what makes horizontal scaling possible, alongside stateless servers.
Q3Replication vs sharding?
AReplication keeps copies of the same data on multiple nodes — typically primary for writes and replicas for reads, scaling reads and adding redundancy, with slight replica lag. Sharding splits different data across databases by a shard key, scaling writes and storage beyond one machine, at the cost of harder cross-shard queries and the risk of hot shards from a poor key.
Q4Explain the CAP theorem.
AIn a distributed system you can guarantee at most two of consistency, availability, and partition tolerance. Since network partitions are inevitable, P is required, so the real trade-off during a partition is consistency versus availability — either reject requests to stay consistent, or stay available and risk serving stale data. Many large-scale systems pick availability with eventual consistency.
Q5SQL or NoSQL — how do you decide?
AI start from the data and access patterns. SQL when I need ACID transactions, relationships, and complex queries — and it scales well with indexing, read replicas, and caching. NoSQL when access patterns are simple and I need very high write throughput or horizontal scale beyond a relational DB. I don't default to NoSQL just for "scale"; I justify it from the requirements.
