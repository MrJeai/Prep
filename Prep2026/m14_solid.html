What SOLID Is

Five principles for code that's easy to change

SOLID is five object-oriented design principles (coined by Robert C. Martin) that together make code easier to maintain, extend, and test. They're not rules to follow blindly — they're guidelines that fight specific kinds of fragility.

LetterPrincipleOne-line idea
SSingle ResponsibilityA class should have one reason to change.
OOpen/ClosedOpen for extension, closed for modification.
LLiskov SubstitutionSubtypes must be usable as their base type.
IInterface SegregationMany small interfaces beat one fat one.
DDependency InversionDepend on abstractions, not concretions.
02

S — Single Responsibility

One class, one reason to change
📖 Principle
A class should have one responsibility — one reason to change. If a class does report generation and emailing and saving, three unrelated forces can break it.
❌
Violation
InvoiceService calculates totals, formats a PDF, and sends email.
→ A change to email logic risks breaking invoice math.
✅
Fix
Split into InvoiceCalculator, PdfRenderer, EmailSender.
→ Each changes for one reason; each is independently testable.
03

O — Open/Closed

Extend behaviour without editing existing code
📖 Principle
Software should be open for extension but closed for modification. You add new behaviour by adding new code, not by editing tested, working code.
C#❌ violation — must edit on every new type
decimal Discount(Customer c) {
  if (c.Type == "Regular") return 0;
  if (c.Type == "Premium") return 0.1m;  // new type ⇒ edit this method
}
C#✅ fix — add a class, don't touch the rest
interface IDiscount { decimal Rate(); }
class Premium : IDiscount { public decimal Rate() => 0.1m; }
// add Vip : IDiscount later — existing code untouched
💡 Note
Open/Closed is usually achieved with abstraction + polymorphism (interfaces, inheritance, the Strategy pattern from Module 15).
04

L — Liskov Substitution

A subtype must honour the base type's contract
📖 Principle
Objects of a subclass must be substitutable for their base class without breaking the program. A subtype that can't do what its base promises violates LSP.
❌
The classic violation
Square : Rectangle — setting Width also forces Height, breaking code that assumed independent sides. Or Ostrich : Bird with a Fly() that throws.
✅
Fix
Don't force an "is-a" that breaks the contract. Model capabilities with separate abstractions (e.g. IFlyingBird) instead of inheriting behaviour a subtype can't fulfil.
⚠️ The signal
If a subclass overrides a method to throw NotSupportedException, or callers must check the concrete type, LSP is being violated.
05

I — Interface Segregation

Don't force clients to depend on methods they don't use
📖 Principle
Prefer many small, focused interfaces over one large "fat" interface. A class shouldn't be forced to implement methods it doesn't need.
C#
// ❌ fat interface — a SimplePrinter is forced to implement Scan/Fax
interface IMachine { void Print(); void Scan(); void Fax(); }

// ✅ segregated — implement only what applies
interface IPrinter { void Print(); }
interface IScanner { void Scan(); }
06

D — Dependency Inversion

High-level code shouldn't depend on low-level details
📖 Principle
High-level modules and low-level modules should both depend on abstractions, not on each other. Abstractions shouldn't depend on details; details depend on abstractions.
C#
// ❌ OrderService depends on a concrete SqlOrderRepo
class OrderService { SqlOrderRepo _r = new(); }

// ✅ depend on the interface; the concrete is injected (Module 5)
class OrderService {
  private readonly IOrderRepo _r;
  public OrderService(IOrderRepo r) => _r = r;
}
💡 Full-circle
This is the principle behind both Dependency Injection (Module 5) and Clean Architecture's Dependency Rule (Module 13). DIP is the "why"; DI is the "how".
07

Interview Preparation

Questions and model answers at the 4 YOE level
Q1Explain the Single Responsibility Principle with an example.
AA class should have one reason to change. If an InvoiceService calculates totals, renders a PDF, and sends email, three unrelated concerns can break it. Splitting into calculator, renderer, and sender means each changes for one reason and is independently testable.
Q2What does Open/Closed mean in practice?
AYou should add new behaviour by adding code, not by editing existing tested code. Instead of a growing if/switch on a type, define an interface and add a new implementing class for each case — typically via polymorphism or the Strategy pattern. Existing code stays untouched.
Q3Give a Liskov violation.
ASquare inheriting Rectangle: setting width also changes height, breaking callers that assume independent sides. Or an Ostrich subclass of Bird whose Fly() throws. The fix is to not force an is-a relationship the subtype can't honour — model capabilities with separate abstractions. A subclass overriding a method to throw NotSupportedException is the tell.
Q4Interface Segregation — why?
ASo clients don't depend on methods they don't use. A fat IMachine with Print/Scan/Fax forces a simple printer to implement Scan and Fax it can't do. Splitting into IPrinter, IScanner lets each class implement only what applies, keeping interfaces cohesive.
Q5How does Dependency Inversion relate to DI?
ADIP says high-level and low-level modules should both depend on abstractions, not on each other. Dependency Injection is how you achieve it in practice — a class declares an interface in its constructor and the container supplies the concrete implementation. DIP is the principle; DI is the mechanism, and it's also the basis of Clean Architecture's dependency rule.
