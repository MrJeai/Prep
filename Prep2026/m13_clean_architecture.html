Clean Architecture

Product companies care less about whether you can write a feature and more about how you structure it. Clean Architecture is the answer most teams converge on: clear layers, a strict dependency direction, and business logic kept independent of frameworks and databases. This module covers the layers, the patterns that live in them (Repository, CQRS, MediatR), and the supporting libraries.

Interview ROI: High

01

Why Layering

Separation of concerns, made concrete

When everything lives in the controller — HTTP handling, business rules, SQL — you get code that's impossible to test, reuse, or change safely. Clean Architecture separates responsibilities into layers so each has one job, and arranges the dependencies so your business logic doesn't depend on the database or the web framework.

📖 The core idea
Business rules are the most valuable, longest-lived part of your system. Frameworks, databases, and UIs are details that change. Clean Architecture protects the core from the details by making the details depend on the core, never the other way around.
02

The Layers & the Dependency Rule

Four rings, one direction of dependency
1
Presentation / API
Controllers, DTOs, model binding. HTTP only. (Modules 8 & 12.)
↓ depends on
2
Application
Use cases / services, orchestration, interfaces (e.g. IOrderRepository). No framework code.
↓ depends on
3
Domain (core)
Entities and business rules. Pure C#. Depends on nothing.
↑ implements interfaces from Application
4
Infrastructure
EF Core, external APIs, email, file storage — the "details".
📖 The Dependency Rule
Source-code dependencies point inward only. Domain depends on nothing; Application depends on Domain; Presentation and Infrastructure depend on Application/Domain — never the reverse. Infrastructure implements interfaces declared in the inner layers, so the core defines what it needs and the outer layer supplies how. This is the Dependency Inversion Principle (Module 14) applied at architecture scale, wired together with DI (Module 5).
💡 The payoff
You can swap SQL Server for Postgres, or the web framework, without touching business logic. You can unit-test the core with no database. That testability and changeability is exactly what interviewers are probing for.
03

The Repository Pattern

Useful — but know when EF Core already covers it

A repository abstracts data access behind an interface (IOrderRepository with GetByIdAsync, AddAsync…), so the Application layer depends on the interface, not on EF Core. This keeps persistence in Infrastructure and makes services testable with a mock repository.

⚠️ The nuanced take interviewers reward
DbContext is already a Unit of Work and DbSet is already a repository (Module 10). So wrapping EF in a generic repository can be redundant ceremony. The mature answer: "I use repositories when I want to keep the domain free of EF and make testing easy, but I avoid a thin generic repository that just re-wraps DbSet for no benefit." Showing you know both sides beats dogma.
04

CQRS & MediatR

Separating reads from writes, and decoupling the caller
4.1 — CQRS

CQRS (Command Query Responsibility Segregation) separates operations that change state (Commands) from those that read state (Queries). Each becomes its own handler with its own model. Reads and writes often have very different shapes and performance needs, so splitting them keeps each simple.

📖 Command vs Query
A Command changes data and typically returns little (CreateOrder). A Query returns data and changes nothing (GetOrderById). At its simplest CQRS is just this separation — it does not require separate databases or event sourcing (those are advanced extensions).
4.2 — MediatR

MediatR is a library that implements the mediator pattern: instead of a controller calling a service directly, it sends a request (a command or query) and MediatR routes it to the matching handler. The controller no longer knows about the handler, and cross-cutting concerns (logging, validation) can be slotted in as pipeline behaviors.

C#
// Controller just sends; doesn't know the handler
var result = await _mediator.Send(new GetOrderQuery(id));
💡 Balanced view
CQRS + MediatR is common in Clean Architecture codebases and great interview vocabulary, but it adds indirection. For a small CRUD API a plain service layer is fine. Know it, and know when it's overkill.
05

AutoMapper & FluentValidation

The two supporting libraries you'll be asked about
AutoMapper
Maps between entities and DTOs automatically by convention, removing hand-written mapping code.
  • Pro: less boilerplate.
  • Con: hidden mappings can obscure bugs; many teams now prefer explicit mapping or projection.
FluentValidation
Expresses validation as readable, testable C# rules instead of attributes (Module 8).
  • Great for complex, cross-field rules.
  • Plugs into the request pipeline (or MediatR behavior).
📝 How it ties together
In a Clean Architecture API: the controller (Presentation) sends a command via MediatR → a FluentValidation behavior validates it → the handler (Application) runs business logic against domain entities → a repository (Infrastructure) persists via EF Core → AutoMapper (or projection) shapes the result into a DTO to return. Every module you've learned has a place here.

Interview Preparation

Questions and model answers at the 4 YOE level
Q1What is Clean Architecture and what's its core rule?
AIt organises code into layers — Domain, Application, Infrastructure, Presentation — with the Dependency Rule: source-code dependencies point inward only. Domain depends on nothing; outer layers depend on inner ones. Infrastructure implements interfaces defined in the inner layers, so business logic stays independent of the database and framework, which makes it testable and changeable.
Q2Do you always need the Repository pattern with EF Core?
ANot always. DbContext is already a Unit of Work and DbSet is already a repository, so a thin generic repository over EF can be redundant. I use repositories to keep the domain free of EF and to ease testing, but I avoid wrapping DbSet just for the sake of a pattern.
Q3What is CQRS?
ACommand Query Responsibility Segregation — separating operations that change state (commands) from those that read state (queries), each with its own model and handler. It keeps reads and writes simple since they often differ in shape and performance. It doesn't require separate databases; that's an advanced extension.
Q4What does MediatR give you?
AIt implements the mediator pattern: controllers send a request and MediatR dispatches it to the right handler, decoupling caller from handler. Cross-cutting concerns like validation and logging can be added as pipeline behaviors. It's common in Clean Architecture but adds indirection, so it's overkill for simple CRUD.
Q5How does the Dependency Rule relate to DI and SOLID?
AIt's the Dependency Inversion Principle applied at the architecture level: inner layers define interfaces, outer layers implement them, and DI wires the implementations in at startup. So the core depends on abstractions while the concrete details depend on the core.
