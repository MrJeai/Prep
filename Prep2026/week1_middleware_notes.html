01

What is Middleware?

Concept, Definition, and the Mental Model
1.1 — The Problem Middleware Solves

Before ASP.NET Core, the classic ASP.NET Framework relied on HttpModules and HttpHandlers to process HTTP requests. These components were tightly coupled to IIS — the Microsoft web server — which meant you couldn't run them on Linux, couldn't reorder them easily, and testing them in isolation was painful.

When the ASP.NET Core team redesigned the framework from scratch, they introduced a new, clean abstraction: the middleware pipeline. This is a sequence of software components — called middleware — through which every HTTP request passes before reaching your application logic, and through which every HTTP response passes on its way back to the client.

📖 Definition
Middleware is a software component that sits in the HTTP request-response pipeline. Each middleware component receives an incoming HttpContext object, performs some work (logging, authentication, routing, etc.), and then either passes control to the next middleware in the chain, or short-circuits the pipeline by returning a response immediately without calling the next component.

Every middleware is aware of two things: what comes before it (because it was called by the previous middleware) and what comes after it (because it holds a reference to the next middleware, called the RequestDelegate). This creates a chain, often described as a Russian nesting doll or Matryoshka structure.

1.2 — The Matryoshka Mental Model

Imagine each middleware as a layer of the Russian nesting doll. A request enters the outermost layer, travels inward through each layer until it reaches the core handler (your controller or endpoint), and then the response travels outward through each layer in reverse order. This is why middleware can do work both before and after the rest of the pipeline runs.

OUTERMOST — Runs first on request, last on response
🛡️ Exception Handler Middleware
🔀 HTTPS Redirection + Static Files
🗺️ Routing Middleware
🔑 Authentication Middleware
🧱 Authorization Middleware
⚙️ Controller / Endpoint Handler
The actual application logic
💡 Key Insight
The request travels from top to bottom (outer to inner). The response travels from bottom to top (inner to outer). This means each middleware has an opportunity to both pre-process the request and post-process the response.
1.3 — Real-World Analogy: Airport Security

Think of the middleware pipeline as the stages a passenger goes through at an airport. Each checkpoint is a middleware component. The passenger is the HTTP request.

1

→ Analogous to Routing — the request is identified and directed correctly
↓

📝 Important Note
If security rejects the passenger at step 2 (because the person has no valid ID), they never reach the boarding gate. This is exactly what short-circuiting means in middleware — stopping the pipeline at a particular point and returning a response early, without calling any further middleware.
02

Internal Architecture

How the Pipeline is Constructed at Startup
2.1 — The RequestDelegate Chain

At the heart of the middleware system is a delegate called RequestDelegate. Its signature is deceptively simple:

C#
public delegate Task RequestDelegate(HttpContext context);

Every middleware component receives a RequestDelegate pointing to the next middleware in the chain. When a middleware calls await next(context), it is literally invoking the next middleware's handler function. When a middleware does not call next, the pipeline stops at that point.

2.2 — How IApplicationBuilder Builds the Chain

When you call app.Use(), app.Run(), or app.UseMiddleware<T>() in Program.cs, you are not immediately running the middleware. Instead, you are registering a middleware factory — a function that, when given the next RequestDelegate, produces the current middleware's RequestDelegate.

The type of each factory is:

C#
Func<RequestDelegate, RequestDelegate>

IApplicationBuilder stores a list of these factories internally. At application startup, ASP.NET Core calls Build() on the IApplicationBuilder. The Build() method iterates through the registered factories in reverse order, chaining each one to the next, and produces a single composed RequestDelegate that represents the entire pipeline.

📝 Critical Fact for Interviews
The pipeline is built exactly once at application startup and reused for every request. This means constructing the pipeline has no per-request overhead. Middleware objects themselves behave like singletons in terms of their lifecycle within the pipeline structure.
2.3 — Visualising Request and Response Flow

A common way to draw the pipeline in an interview is as a linear sequence where each middleware wraps the next. Below is a clean representation of how the request flows in, and the response flows back out:

// Request → (top to bottom) | Response ← (bottom to top)
Client Request ──►
  [ExceptionHandlerMiddleware]  before↓  after↑
    [HttpsRedirectionMiddleware]  before↓  after↑
      [RoutingMiddleware]          before↓  after↑
        [AuthMiddleware]           before↓  after↑
          [AuthZMiddleware]         before↓  after↑
            ⚙️ Controller/Endpoint Handler
          [AuthZMiddleware]         ◄── after runs
        [AuthMiddleware]           ◄── after runs
      [RoutingMiddleware]          ◄── after runs
    [HttpsRedirectionMiddleware] ◄── after runs
  [ExceptionHandlerMiddleware]  ◄── after runs (catches any exception here)
◄── Response sent to Client

Notice that ExceptionHandlerMiddleware is registered first (outermost) so that its "after" logic runs last, making it the catch-all safety net for the entire pipeline.

03

Writing Middleware

Three Approaches — Lambda, Terminal, and Class-Based
3.1 — Overview of All Three Approaches

ASP.NET Core gives you three ways to write and register middleware. Understanding all three — when to use each and why — is a key interview topic at the 4 YOE level.

app.Use()
  • Inline lambda
  • Calls next() to continue
  • Good for quick, simple logic
  • Not suitable for complex or reusable middleware
app.Run()
  • Terminal — never calls next
  • Always short-circuits the pipeline
  • Good for final response writers
  • Any middleware added after it is unreachable
Class-based ⭐
  • Convention-based class
  • Production standard
  • Supports DI injection
  • Registered via extension method
3.2 — Approach 1: Inline Lambda with app.Use()

The simplest form of middleware is a lambda function passed to app.Use(). This form is appropriate for one-liners or small, non-reusable logic. The lambda receives the HttpContext and a RequestDelegate named next.

C#Program.cs
// Inline lambda middleware
app.Use(async (context, next) =>
{
    // Code here runs BEFORE the next middleware
    Console.WriteLine($"[BEFORE] {context.Request.Path}");

    await next(context);  // Pass control to the next middleware

    // Code here runs AFTER the next middleware has completed
    Console.WriteLine($"[AFTER] Status: {context.Response.StatusCode}");
});
⚠️ Watch Out
In older ASP.NET Core versions, the next parameter was a Func<Task> and called without passing context: await next(). In .NET 6+ and the minimal API style, next is a RequestDelegate and you must pass the context explicitly: await next(context). Both styles still exist in codebases you will encounter.
3.3 — Approach 2: Terminal Middleware with app.Run()

A middleware registered with app.Run() is always terminal — it does not receive a next parameter and never calls the next component. The pipeline ends here and the response is written immediately.

C#Program.cs
// Terminal middleware — pipeline ends here
app.Run(async context =>
{
    context.Response.StatusCode = 200;
    await context.Response.WriteAsync("Pipeline ends here. No further middleware runs.");
});

// Any middleware registered AFTER app.Run() is NEVER executed
app.Use(async (context, next) => { /* This is unreachable */ });
📝 Remember
app.Run() is appropriate when you want to write a final "catch-all" response. For example, a health-check endpoint that writes 200 OK for /health and nothing else. In practice, you typically use it as the final fallback at the bottom of the pipeline.
3.4 — Approach 3: Class-Based (Convention) Middleware ⭐ Production Standard

For any real-world middleware beyond trivial logic, you should write a dedicated class. This is the pattern used by all of ASP.NET Core's built-in middlewares. The convention requires:

  • A public class with a constructor that accepts a RequestDelegate as its first parameter.
  • A public method named InvokeAsync (or Invoke) that accepts HttpContext as its first parameter and returns Task.

Here is a complete, production-grade example of a request timing and logging middleware:

C#Middleware/RequestLoggingMiddleware.cs
using System.Diagnostics;

public class RequestLoggingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestLoggingMiddleware> _logger;

    // Constructor — ASP.NET Core injects RequestDelegate and singleton/transient services here
    public RequestLoggingMiddleware(
        RequestDelegate next,
        ILogger<RequestLoggingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    // InvokeAsync is called for every HTTP request
    public async Task InvokeAsync(HttpContext context)
    {
        var sw = Stopwatch.StartNew();

        _logger.LogInformation(
            "→ Incoming Request: {Method} {Path}",
            context.Request.Method,
            context.Request.Path);

        await _next(context);  // Passes to next middleware / endpoint

        sw.Stop();
        _logger.LogInformation(
            "← Response: {StatusCode} in {ElapsedMs}ms",
            context.Response.StatusCode,
            sw.ElapsedMilliseconds);
    }
}
C#Middleware/RequestLoggingMiddlewareExtensions.cs
// Extension method — this is the clean, production way to register custom middleware
public static class RequestLoggingMiddlewareExtensions
{
    public static IApplicationBuilder UseRequestLogging(
        this IApplicationBuilder app)
    {
        return app.UseMiddleware<RequestLoggingMiddleware>();
    }
}

// Program.cs — Clean, readable registration:
app.UseRequestLogging();  // vs. app.UseMiddleware<RequestLoggingMiddleware>() directly
✅ Best Practice
Always create an extension method (UseXxx) for your custom middleware. This is how all built-in ASP.NET Core middleware is registered (UseAuthentication(), UseRouting(), etc.) and it makes your Program.cs clean and readable.
3.5 — Scoped Service Injection: The InvokeAsync Pattern

This is one of the most important nuances of middleware and a frequent interview question. Because middleware classes are constructed once at startup (essentially singleton behavior), you cannot inject scoped services (like a DbContext or a repository that is scoped per-request) through the constructor. Doing so creates what is known as the Captive Dependency problem — the scoped service would be held alive for the entire application lifetime, causing incorrect behavior and data leaks.

The solution is to inject scoped services as additional parameters to InvokeAsync. ASP.NET Core's middleware activation mechanism supports method injection — it resolves additional parameters of InvokeAsync from the per-request DI scope.

C#Correct: Scoped Service via InvokeAsync
public class CurrentUserMiddleware
{
    private readonly RequestDelegate _next;
    // ✅ ILogger is a singleton — safe to inject via constructor
    private readonly ILogger<CurrentUserMiddleware> _logger;

    public CurrentUserMiddleware(RequestDelegate next,
        ILogger<CurrentUserMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    // ✅ IUserRepository is scoped — inject here, NOT in constructor
    public async Task InvokeAsync(HttpContext context,
        IUserRepository userRepository) // ← per-request scope
    {
        var userId = context.User.FindFirst("sub")?.Value;
        if (userId != null)
        {
            var user = await userRepository.GetByIdAsync(userId);
            context.Items["CurrentUser"] = user;
        }
        await _next(context);
    }
}
❌ Never Do This
Never inject a scoped service (like AppDbContext or IUserRepository with scoped lifetime) through the constructor of a middleware class. The middleware lives as long as the application — so the scoped service will never be disposed and will hold database connections indefinitely.
3.6 — Sharing Data Between Middlewares: HttpContext.Items

Often, an upstream middleware (e.g., one that resolves the current user from a JWT) needs to pass data to a downstream middleware or controller. The appropriate mechanism for this is HttpContext.Items, which is a IDictionary<object, object?> that is scoped to the lifetime of a single HTTP request.

C#Passing data downstream via HttpContext.Items
// In Middleware A — writing data
context.Items["CorrelationId"] = Guid.NewGuid().ToString();

// In Middleware B (downstream) or in a Controller — reading data
var correlationId = context.Items["CorrelationId"] as string;

// In a Controller (via IHttpContextAccessor)
var correlationId = _httpContextAccessor.HttpContext?.Items["CorrelationId"];
💡 Pro Tip
To avoid Items key collisions in large codebases (especially when using third-party middleware), use typed keys rather than plain strings. Define a static class with unique key objects, or use the type itself as the key: context.Items[typeof(CurrentUser)] = user;
04

Built-in Pipeline & Ordering

The Correct Sequence and Why It Matters
4.1 — Why Order is Non-Negotiable

Order is not a matter of style in ASP.NET Core middleware — it is a matter of correctness. Placing a middleware in the wrong position causes real, often subtle bugs. The most common interview question in this area is: "What is the correct order of middleware in ASP.NET Core and why?" Here is the answer, with explanation for each decision.

4.2 — The Standard Pipeline Order (.NET 8)
C#Program.cs — Correct Middleware Order
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddControllers();
var app = builder.Build();

// ① Must be first — it wraps everything so it can catch all exceptions
app.UseExceptionHandler("/error");

// ② Redirects HTTP → HTTPS early, before any real processing
app.UseHttpsRedirection();

// ③ Serves files from wwwroot, short-circuits if a static file matches
app.UseStaticFiles();

// ④ Resolves which endpoint the request maps to (adds endpoint metadata)
app.UseRouting();

// ⑤ Reads the JWT/cookie and populates HttpContext.User
app.UseAuthentication();

// ⑥ Checks if HttpContext.User has permission for the resolved endpoint
app.UseAuthorization();

// ⑦ Executes the matched controller action or minimal API endpoint
app.MapControllers();

app.Run();
4.3 — Detailed Explanation of Each Position
1
UseExceptionHandler
Outermost wrapper. Any unhandled exception thrown anywhere downstream is caught here and converted to a structured error response.
SAFETY NET
2
UseHttpsRedirection
If a request arrives on plain HTTP, immediately redirect to HTTPS. Must be early — before authentication so that credentials aren't accidentally sent over plain HTTP.
SECURITY
3
UseStaticFiles
If the request path matches a file in wwwroot (e.g., /style.css), serve it and short-circuit. No need to run auth or routing for static assets.
PERFORMANCE
4
UseRouting
Resolves the matching endpoint for the request and attaches endpoint metadata (like [Authorize] attribute info) to HttpContext. Authorization depends on this metadata.
ROUTING
5
UseAuthentication
Reads the Authorization header or cookie, validates the token, and if valid, constructs a ClaimsPrincipal and assigns it to HttpContext.User.
WHO ARE YOU?
6
UseAuthorization
Reads HttpContext.User (set by Authentication) and checks if the user has the required permissions for the matched endpoint (set by Routing). Both must run first.
ARE YOU ALLOWED?
7
MapControllers / Endpoint
Executes the controller action or minimal API endpoint handler that was matched by routing. This is where your actual business logic runs.
BUSINESS LOGIC
❌ Classic Bug
If you place UseAuthorization() before UseAuthentication(), the HttpContext.User will be an empty, unauthenticated identity when authorization runs. Every request will fail with 403 Forbidden, even with a valid token. Similarly, placing UseAuthentication() before UseRouting() means the endpoint metadata — including [AllowAnonymous] attributes — is not yet available, causing incorrect authorization decisions.
4.4 — Short-Circuiting the Pipeline

A middleware short-circuits the pipeline by simply not calling next(context) and instead writing directly to the response. This is a deliberate, controlled stop of the request pipeline — used for API key validation, authentication failures, maintenance mode, rate limiting, etc.

C#ApiKeyMiddleware.cs — Short-circuit example
public async Task InvokeAsync(HttpContext context)
{
    if (!context.Request.Headers.TryGetValue("X-Api-Key", out var extractedApiKey))
    {
        // ❌ No API key header — short-circuit here
        context.Response.StatusCode = 401;
        await context.Response.WriteAsync("Missing API Key.");
        return;  // ← Pipeline stops. No next() called. No controller runs.
    }

    if (extractedApiKey != _validApiKey)
    {
        context.Response.StatusCode = 401;
        await context.Response.WriteAsync("Invalid API Key.");
        return;
    }

    // ✅ Valid API key — continue to the next middleware
    await _next(context);
}
05

Advanced Patterns

Map, UseWhen, MapWhen — Branching the Pipeline
5.1 — Branching with Map()

The app.Map() method creates a separate sub-pipeline that runs only for requests whose path starts with a given prefix. Requests that match the branch path do not continue into the main pipeline. This is useful for creating completely separate request handling areas — such as a health-check endpoint, a WebSocket endpoint, or a maintenance-mode handler.

C#Branching with Map()
app.Map("/health", healthApp =>
{
    // This sub-pipeline ONLY handles requests to /health
    healthApp.Run(async context =>
    {
        context.Response.ContentType = "application/json";
        await context.Response.WriteAsync("{ \"status\": \"healthy\" }");
    });
});

// The main pipeline only runs for requests that do NOT start with /health
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();
5.2 — Conditional Middleware with UseWhen()

Unlike Map(), UseWhen() does not create a permanent fork — after the conditional branch executes, the request continues in the main pipeline. It runs a custom middleware sub-pipeline only when a predicate is true.

C#UseWhen — runs only for /api paths
app.UseWhen(
    context => context.Request.Path.StartsWithSegments("/api"),
    apiApp =>
    {
        // This extra middleware only runs for /api/* requests
        apiApp.Use(async (context, next) =>
        {
            Console.WriteLine("API-specific middleware running");
            await next(context);
        });
    }
);

// The main pipeline continues after the branch for ALL requests
app.UseRouting();
📝 Map vs UseWhen
Map: The branch is exclusive. Requests that match the path do NOT rejoin the main pipeline afterward.
UseWhen: The branch is conditional. After the branch's middleware runs, the request does rejoin the main pipeline and continues.

Common Mistakes

What Gets Engineers Rejected in Code Reviews and Interviews
❌
UseAuthorization() before UseAuthentication()
Authorization middleware checks HttpContext.User. If Authentication hasn't run yet, User is an anonymous, empty identity. Every authenticated request appears unauthorized.
✅ Fix: Always place UseAuthentication() immediately before UseAuthorization().
❌
UseRouting() after UseAuthorization()
Routing attaches endpoint metadata (including [AllowAnonymous] attributes) to the request context. If routing hasn't run, authorization cannot inspect this metadata and makes incorrect decisions.
✅ Fix: UseRouting → UseAuthentication → UseAuthorization, always in this sequence.
❌
Injecting a Scoped Service in the Constructor
Middleware lives as a singleton (effectively). Injecting a scoped service like DbContext in the constructor creates a "captive dependency" — the scoped service is never properly disposed and the middleware holds a stale database connection for the app's lifetime.
✅ Fix: Inject scoped services as parameters in InvokeAsync(), not the constructor.
❌
Forgetting to await next(context)
If you write _next(context); without await, the middleware returns before the rest of the pipeline finishes executing. Post-processing code after _next runs before the response is ready, leading to subtle, hard-to-debug timing issues.
✅ Fix: Always write await _next(context);
❌
Writing to the response after calling next()
Once a downstream middleware or controller writes status code and headers, the response has started. Attempting to modify headers or write to the response body after _next(context) returns will throw a InvalidOperationException.
✅ Fix: Always check context.Response.HasStarted before writing post-next. Read only; do not modify.
❌
Placing UseExceptionHandler anywhere but first
Exception handling middleware only catches exceptions thrown by middleware that runs after it. Placing it anywhere other than the top means exceptions thrown before it is reached are completely unhandled.
✅ Fix: UseExceptionHandler() must be the very first middleware registered.

Interview Preparation

Questions and Model Answers at the 4 YOE Level
Q1What is the middleware pipeline in ASP.NET Core? How is it different from HttpModules in classic ASP.NET?
AThe middleware pipeline is an ordered chain of components, each represented as a RequestDelegate, that processes every HTTP request and response. Unlike HttpModules in classic ASP.NET, which were tightly coupled to IIS and configured in web.config, ASP.NET Core's pipeline is fully code-driven, server-agnostic (works on Kestrel, nginx, IIS), and highly composable. You can reorder, add, or remove components in code, which also makes it testable in isolation.
Q2What is the difference between Use(), Run(), and Map()?
A
MethodCalls next?Use Case
Use()Optionally (you decide)Standard middleware with before/after logic. Calls next to continue, or skips it to short-circuit.
Run()NeverTerminal middleware — always ends the pipeline. Suitable for final response writers.
Map()BranchesCreates an exclusive sub-pipeline for a path prefix. Requests that match do not rejoin the main pipeline.
Q3Why does middleware order matter? Give a concrete example of what breaks if you get it wrong.
ABecause each middleware sees only the state left by the middlewares before it. A classic example: placing UseAuthorization() before UseAuthentication(). Authentication is responsible for reading the JWT and populating HttpContext.User. If authorization runs first, User is still an unauthenticated principal, so every protected endpoint returns 403 Forbidden even when a valid token is sent.
Q4What is short-circuiting in middleware? When would you use it?
AShort-circuiting means a middleware intentionally does not call next(context), preventing any further middleware or controllers from running. It is used when the request should be rejected or handled entirely at this stage — for example, an API key middleware that returns 401 if no valid key is present, a rate limiter that returns 429 if the client has exceeded their quota, or a maintenance mode middleware that returns 503 for all traffic during a deployment.
Q5Why can't you inject a scoped service in a middleware's constructor? How do you solve this?
AMiddleware is constructed once at application startup and reused for every request — so its constructor dependencies are resolved only once and kept for the application's entire lifetime. Scoped services are designed to live for one request and then be disposed. If you inject a scoped service in a middleware constructor, it becomes a captive dependency: never disposed, holding resources (like database connections) indefinitely. The solution is to inject scoped services as additional parameters in InvokeAsync(). ASP.NET Core resolves these parameters from the per-request DI scope, so they are properly created and disposed for each request.
Q6What is the difference between middleware and MVC filters?
AMiddleware operates at the HTTP pipeline level, before MVC or routing. It runs on every request, regardless of whether it eventually reaches a controller or not. Filters are part of MVC's action execution pipeline and only run for requests that have matched a controller action. Filters have access to richer MVC context — ActionContext, ModelState, action arguments — that middleware cannot access. Choose middleware for cross-cutting concerns that apply broadly (logging, auth, CORS, compression); choose filters for concerns specific to controller actions (input validation, action-level caching, model binding customisation).
