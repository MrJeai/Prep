High-Level Design (HLD)

HLD rounds ask you to architect a whole system on a whiteboard. What's graded is your method: do you clarify scope, estimate, lay out components, and reason about bottlenecks? This module gives you a repeatable 7-step framework, then applies it to the classic problems so the structure becomes second nature.

The 7-Step Framework

A structure that works for any HLD question
1
Clarify requirements
Functional + non-functional; scope it down. Don't design what wasn't asked.
↓
2
Estimate scale
Users, QPS, read/write ratio, storage. Rough numbers with assumptions.
↓
3
Define API
The key endpoints — the contract (Module 8).
↓
4
High-level components
Client → LB → services → cache → DB → queue. Draw the boxes.
↓
5
Data model & storage choice
SQL vs NoSQL, schema, indexes — justify it (Module 26).
↓
6
Scale it
Add caching, replicas, sharding, CDN, queues where the load demands.
↓
7
Identify bottlenecks & trade-offs
Single points of failure, hot spots, consistency choices.
💡 The meta-point
Drive the conversation with this structure and think aloud. A clear, well-reasoned design beats a "perfect" one delivered silently. Interviewers reward method and communication over a memorised answer.
02

Worked Example — URL Shortener

The framework applied end to end
  • 1Requirements: shorten a long URL → short code; redirect short → long. Non-functional: very read-heavy, low latency, high availability.
  • 2Scale: say 100M new URLs/month, reads ≫ writes (e.g. 100:1). That read-heavy ratio screams caching.
  • 3API: POST /shorten {url} → {shortUrl}; GET /{code} → 301/302 redirect.
  • 4Components: client → load balancer → URL service → cache (Redis) → database.
  • 5Data & code generation: store code → longUrl. Generate the code by base-62 encoding an auto-increment id (or a counter/hash). Simple key-value access fits SQL with an index or a key-value store.
  • 6Scale: cache hot codes in Redis (most reads never touch the DB); read replicas; a CDN/edge for redirects.
  • 7Trade-offs: 301 (permanent, cacheable, fewer hits but no click analytics) vs 302 (lets you count clicks); collision handling on code generation.
📝 Why this is the starter problem
It exercises every fundamental — read-heavy caching, key generation, redirect semantics — in a small scope, so master this one and the framework transfers to the rest.
03

Worked Example — Notification Service

Where queues take centre stage
  • 1Requirements: send notifications across channels (push, email, SMS); handle bursts; retry failures; don't double-send.
  • 2Components: API receives a request → puts a message on a queue (Module 20) → channel workers consume and call providers.
  • 3Why a queue: decouples senders from delivery, absorbs spikes (load levelling), and enables retries with a dead-letter queue for persistent failures.
  • 4Idempotency: consumers dedupe by notification id so at-least-once delivery doesn't double-send (Modules 19–20).
  • 5Scale: add more workers per channel (competing-consumers work queue); separate queues per channel so a slow SMS provider doesn't block email.
💡 Pattern recognition
Any "do work asynchronously, handle spikes, retry on failure" problem is a queue-plus-workers design. Recognising that instantly is half the battle.

More Problems — Key Ideas

The other classics in one line each
ProblemThe crux to mention
Chat / WhatsAppPersistent connections (WebSockets) for real-time delivery; message store; per-user inbox; delivery/read receipts; fan-out for group chats.
E-commerceService decomposition (catalog, cart, order, payment, inventory); strong consistency for payment/inventory; eventual consistency + events elsewhere; idempotent orders.
File upload / storageStore blobs in object storage (S3/Blob), metadata in a DB; pre-signed URLs so clients upload directly; CDN for downloads; chunked uploads for large files.
Rate limiterToken-bucket/sliding-window counter in a shared store (Redis) so the limit is global across instances (Module 18); return 429 when exceeded.
News feedFan-out-on-write (precompute feeds) vs fan-out-on-read (compute on request); cache feeds; the celebrity/hot-key problem.
📝 They reuse the same blocks
Notice every design recombines the same pieces: load balancer, stateless services, cache, DB (replicated/sharded), object storage, and queues. HLD is mostly knowing which blocks to assemble and why.

⚠️ Common pitfalls

Interview Preparation

Questions and model answers at the 4 YOE level
Q1How do you approach an HLD question?
AI follow a structure: clarify functional and non-functional requirements and scope it down; estimate scale and the read/write ratio; define the key API; draw the high-level components — client, load balancer, services, cache, database, queue; choose the data model and storage with justification; then scale it with caching, replicas, sharding, CDN, and queues; and finally call out bottlenecks and trade-offs. I think aloud throughout because method and communication are what's graded.
Q2Design a URL shortener — the essentials.
ATwo operations: shorten and redirect, and it's very read-heavy. I'd generate a short code by base-62 encoding an auto-increment id, store code-to-URL, and front the database with Redis since most reads hit hot codes. Load balancer plus stateless services for scale, read replicas, and a CDN for redirects. Key trade-off is 301 versus 302 — permanent and cacheable but no analytics, versus countable clicks — plus handling code collisions.
Q3When do you introduce a message queue in a design?
AWhenever work can be done asynchronously, traffic is spiky, or I need retries — like a notification service. The queue decouples the request from delivery, levels load so bursts don't crush downstream providers, and supports retries with a dead-letter queue. I make consumers idempotent because delivery is at-least-once.
Q4How would you design file uploads at scale?
AStore the file bytes in object storage like S3 or Azure Blob and keep only metadata in the database. I'd issue pre-signed URLs so clients upload directly to storage instead of through my servers, serve downloads via a CDN, and support chunked uploads for large files. This keeps the app stateless and offloads bandwidth.
Q5What are the most common HLD mistakes?
AJumping to a solution before clarifying scope, over-engineering for scale nobody asked about, ignoring single points of failure, and not stating consistency trade-offs. I avoid them by scoping first, designing to the stated scale, and explicitly naming where I'd trade consistency for availability or add redundancy.
