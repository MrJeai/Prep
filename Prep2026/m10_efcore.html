Fundamentals & DbContext

What an ORM is, and the object at the center of everything
1.1 — What EF Core is

Entity Framework Core is an ORM (Object-Relational Mapper): it maps your C# classes to database tables, so you work with objects and LINQ instead of writing raw SQL and manually reading result rows. You write _db.Products.Where(p => p.Price > 100); EF Core translates that to SQL, runs it, and materialises the rows back into Product objects.

📖 Definition — ORM
An ORM bridges two different worlds: the object world (classes, references, inheritance) and the relational world (tables, rows, foreign keys). It removes most boilerplate data-access code, but — and this is the interview theme — it hides the SQL, so a developer who doesn't understand what it generates writes slow code without realising it.
Coming from .NET Framework…EF Core equivalent
ADO.NET / SqlCommand / DataReaderLINQ queries materialised into entities
EF6 (Windows, EDMX designer)EF Core: cross-platform, code-first, no EDMX
Manual mapping of rows → objectsAutomatic materialisation
1.2 — DbContext and DbSet

The DbContext is the heart of EF Core. It represents a session with the database and is two things at once: a Unit of Work (it batches all your changes and saves them together) and a repository of repositories (each DbSet<T> is a queryable collection mapping to a table).

C#AppDbContext.cs
public class AppDbContext : DbContext
{
    public AppDbContext(DbContextOptions<AppDbContext> options)
        : base(options) { }

    public DbSet<Product> Products => Set<Product>();   // maps to the Products table
    public DbSet<Order>   Orders   => Set<Order>();
}

You register it in Program.cs with the provider and connection string — and as you learned in Module 5, it's Scoped:

C#Program.cs
builder.Services.AddDbContext<AppDbContext>(opt =>
    opt.UseSqlServer(builder.Configuration.GetConnectionString("Default")));
⚠️ DbContext is NOT thread-safe
A single DbContext instance must never be used by two threads at once. That's exactly why it's Scoped (one per request), and why you should never make it a Singleton or share it across parallel tasks. This connects directly to the lifetime rules from Module 5.
1.3 — Code-first vs database-first

Code-first (the modern default): you write C# entity classes, and EF generates the database schema via migrations. Database-first: you have an existing database and scaffold entities from it. Coming from legacy projects you may know database-first/EDMX; for new .NET 8 work, code-first with migrations is standard.

Change Tracking & Query Execution

How EF knows what to save, and when queries actually run
2.1 — The change tracker

When you load an entity, the DbContext starts tracking it — keeping a snapshot. When you modify a property and call SaveChanges(), EF compares the current values to the snapshot, works out exactly what changed, and generates the minimal UPDATE. You never write the UPDATE yourself.

Every tracked entity has a state:

StateMeaningOn SaveChanges
AddedNew, not yet in DBINSERT
ModifiedTracked & a property changedUPDATE
DeletedMarked for removalDELETE
UnchangedTracked, no changesnothing
DetachedNot tracked by the contextnothing
C#
var p = await _db.Products.FindAsync(id);  // now tracked, state = Unchanged
p.Price = 999;                            // change tracker notices → Modified
await _db.SaveChangesAsync();              // emits: UPDATE Products SET Price=999 WHERE Id=...
📝 SaveChanges is one transaction
A single SaveChanges() wraps all pending inserts/updates/deletes in one transaction — they all succeed or all roll back. More on this in Chapter 6.
2.2 — AsNoTracking for reads

Tracking costs memory and CPU (snapshots). For read-only queries — the bulk of an API — you don't need it. AsNoTracking() skips the snapshot and is meaningfully faster:

C#
var list = await _db.Products
    .AsNoTracking()        // read-only → no tracking overhead
    .Where(p => p.IsActive)
    .ToListAsync();
💡 Interview-ready rule
"Track when you intend to update; use AsNoTracking for read-only queries." Saying this unprompted signals you understand EF's cost model, not just its syntax.
2.3 — Deferred execution: IQueryable vs IEnumerable

A LINQ query against a DbSet is an IQueryable — it's an expression tree, not data. Nothing hits the database until you enumerate it (with ToList, First, Count, foreach, etc.). Until then you can keep composing, and EF translates the whole thing into one SQL statement.

🚫 The client-evaluation trap
If you call .ToList() (or .AsEnumerable()) too early and then filter, the Where runs in C# after pulling the whole table into memory. Keep operations on IQueryable so they translate to a SQL WHERE and the database does the filtering. Materialising early is a classic, silent performance killer.

Relationships & Modeling

One-to-many, many-to-many, and how to load related data
3.1 — Modeling relationships

EF Core infers relationships from navigation properties and foreign keys by convention. A one-to-many: an Order has many OrderItems.

C#
public class Order
{
    public int Id { get; set; }
    public List<OrderItem> Items { get; set; } = [];  // navigation
}
public class OrderItem
{
    public int Id { get; set; }
    public int OrderId { get; set; }       // foreign key (convention)
    public Order Order { get; set; }       // back-navigation
}
Configuration approachHowUse when
ConventionsEF infers from property names/typesMost cases — keep it simple
Data Annotations[Key], [ForeignKey], [Required] on propertiesSmall overrides
Fluent APIOnModelCreating + modelBuilderComplex mappings, the most power

Relationship types: one-to-many (most common), one-to-one, and many-to-many (EF Core can manage the join table automatically since EF Core 5).

3.2 — Loading related data: eager, explicit, lazy
Eager (Include)
Load related data up front in one query with .Include().
  • Predictable, usually best.
Explicit
Load on demand later with .Entry(x).Collection(...).LoadAsync().
  • Control over when.
Lazy
Auto-loads when you touch a navigation property.
  • Convenient but causes N+1 — see Ch.5.
C#
// Eager loading — one query with a JOIN
var order = await _db.Orders
    .Include(o => o.Items)
    .FirstOrDefaultAsync(o => o.Id == id);
04

Migrations

Evolving the database schema in lockstep with your code

In code-first, migrations are how schema changes are version-controlled and applied. When you change an entity, you create a migration; EF diffs the current model against the last migration and generates the SQL to move the database forward.

CLIdotnet ef
# create a migration after changing your entities
dotnet ef migrations add AddProductPrice

# apply pending migrations to the database
dotnet ef database update
📖 What a migration contains
Each migration is a C# file with an Up() method (apply the change) and a Down() method (revert it). EF tracks which migrations have run in a special table, __EFMigrationsHistory, so it knows what's already applied and only runs the new ones.
1
Change entity (e.g. add a property)
↓
2
migrations add → EF diffs model, generates Up/Down
↓
3
database update → runs Up, records it in __EFMigrationsHistory
💡 Production tip worth mentioning
In production you rarely run database update from a dev machine. You generate an idempotent SQL script (dotnet ef migrations script --idempotent) and apply it through your deployment pipeline, or apply migrations at startup carefully. Naming migrations descriptively and reviewing the generated SQL before shipping are marks of a careful engineer.

LINQ Performance & the N+1 Problem

The most important performance topic in the entire module
5.1 — The N+1 query problem

This is the EF interview question. N+1 happens when you run one query to fetch a list (1), then trigger one more query per item to load related data (N) — turning a single logical operation into hundreds of round-trips to the database.

💀
N+1 — lazy loading in a loop
var orders = await _db.Orders.ToListAsync();
foreach order → order.Items.Count ← each access fires a SQL query
→ 1 query for orders + N queries for items = N+1 round-trips. With 500 orders, that's 501 queries.
✅
Fix — eager load with Include
await _db.Orders.Include(o => o.Items).ToListAsync();
→ One query (with a JOIN), all data loaded. The N round-trips disappear.
🚫 Why it's so dangerous
N+1 is invisible in development with 10 rows of test data — everything feels fast. In production with 50,000 rows it generates tens of thousands of queries and the endpoint times out. This is the bug that most often takes down real .NET systems, which is exactly why interviewers test it.
5.2 — Project only what you need

Don't load whole entities when you need three columns. Use Select to project straight into a DTO — EF generates a SELECT of only those columns, smaller and faster:

C#
var summaries = await _db.Orders
    .Select(o => new OrderSummaryDto { Id = o.Id, Total = o.Total })
    .ToListAsync();   // SELECT Id, Total — not SELECT *
5.3 — Performance checklist
  • ✓AsNoTracking() for read-only queries.
  • ✓Include (or projection) to avoid N+1 — never lazy-load in a loop.
  • ✓Select into DTOs to fetch only needed columns.
  • ✓Always paginate with Skip/Take — never ToList() a whole table.
  • ✓Keep filtering on IQueryable so the database does the work (Ch.2).
  • ✓Use async methods (ToListAsync, etc.) — ties to Module 9.

Transactions & Concurrency

Keeping data correct when many things happen at once
6.1 — Transactions

As noted, a single SaveChanges() is already atomic — all changes commit together or roll back together. When you need multiple SaveChanges (or other operations) to be one atomic unit, open an explicit transaction:

C#
using var tx = await _db.Database.BeginTransactionAsync();
try
{
    _db.Orders.Add(order);
    await _db.SaveChangesAsync();
    _db.Payments.Add(payment);
    await _db.SaveChangesAsync();
    await tx.CommitAsync();        // both succeed together
}
catch
{
    await tx.RollbackAsync();      // or let dispose roll back
    throw;
}
6.2 — Optimistic concurrency

What if two users load the same record and both save? Without protection, the second silently overwrites the first — the lost update problem. EF Core's standard answer is optimistic concurrency using a concurrency token, typically a rowversion column.

C#
public class Product
{
    public int Id { get; set; }
    public decimal Price { get; set; }
    [Timestamp]
    public byte[] RowVersion { get; set; }  // concurrency token
}
📖 How it works
EF adds the original RowVersion to the WHERE clause of the UPDATE. If another user already changed the row, the version no longer matches, zero rows are affected, and EF throws a DbUpdateConcurrencyException. You then decide what to do: reload and retry, or tell the user "this record changed, please review."
OptimisticPessimistic
AssumesConflicts are rareConflicts are likely
MechanismVersion check at save timeLocks the row while editing
EF CoreBuilt-in (concurrency token)Rare; via explicit DB locks
💡 The senior answer
"EF Core favours optimistic concurrency with a rowversion token. It's cheaper than locking because it doesn't hold a lock during the user's think-time; you only pay if an actual conflict occurs, which you handle by catching DbUpdateConcurrencyException and reloading."

Interview Preparation

The questions this module is built to answer
Q1What is the N+1 problem and how do you fix it?
AIt's when you run one query to load a list, then one extra query per item to load related data — N+1 round-trips. It usually comes from lazy-loading a navigation property inside a loop. You fix it by eager-loading with Include (one query with a JOIN) or by projecting the needed data with Select. It's dangerous because it's invisible with small dev data but cripples production with large data.
Q2What is DbContext and what lifetime should it have?
AIt represents a session with the database and acts as a Unit of Work plus a set of queryable DbSets. It should be Scoped — one per HTTP request — because it's not thread-safe and its change tracker represents a single unit of work. Singleton would share it unsafely across requests; Transient would break the unit of work.
Q3How does change tracking work?
AWhen EF loads an entity it keeps a snapshot and marks it Unchanged. As you modify properties the state becomes Modified (or Added/Deleted). On SaveChanges, EF compares current values to the snapshot, generates the minimal INSERT/UPDATE/DELETE, and runs them in one transaction. For read-only queries you skip this overhead with AsNoTracking.
Q4IQueryable vs IEnumerable in EF?
AIQueryable builds an expression tree that EF translates to SQL — operations are executed in the database and nothing runs until you enumerate (deferred execution). Once you switch to IEnumerable (e.g. by calling ToList early), further operations run in memory in C#. Filtering on IEnumerable after materialising means you've already pulled the whole table — a common performance bug.
Q5Eager vs lazy vs explicit loading?
AEager loads related data up front with Include in one query — usually the safe default. Explicit loads it on demand later via the Entry API. Lazy auto-loads when you access a navigation property, which is convenient but the main cause of N+1. Most production code prefers eager loading or projection.
Q6How does EF Core handle concurrent updates?
AWith optimistic concurrency via a concurrency token, typically a rowversion. EF includes the original version in the UPDATE's WHERE clause; if another user changed the row, no rows match and EF throws DbUpdateConcurrencyException, which you handle by reloading and retrying or informing the user. It avoids holding locks during user think-time.
Q7What are migrations and what's in __EFMigrationsHistory?
AMigrations are version-controlled schema changes generated by diffing your model against the last migration; each has Up and Down methods. __EFMigrationsHistory is a table EF maintains listing which migrations have already been applied, so database update only runs the new ones.
