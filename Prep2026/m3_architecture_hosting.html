01

The Hosting Model

Who is in charge of your app's lifetime — and how that changed
1.1 — The old world: IIS was the boss

In classic ASP.NET (Framework), IIS controlled your application's lifetime. You didn't write a Main() method; IIS loaded your app into a worker process (w3wp.exe), decided when to start, recycle, and stop it, and handed requests to System.Web. Your code was a guest inside IIS. That's why old apps couldn't run without IIS and couldn't run off Windows.

1.2 — The new world: your app is a normal program

An ASP.NET Core app is just a console application with a Main() method that starts a web server. You own the lifetime. Inside that program, the framework builds a Host — an object that wires up and manages all the infrastructure your app needs before it can serve a single request.

📖 Definition — The Host
The Host is the container that sets up and owns your app's cross-cutting infrastructure: the Dependency Injection container, the configuration system, the logging system, and the web server (Kestrel). When the host starts, all of these come to life; when it stops, they shut down gracefully. Since .NET 6, you create it with one line: WebApplication.CreateBuilder(args).
📝 The "minimal hosting model" (.NET 6+)
Older Core apps split startup across two files: Program.cs (build the host) and Startup.cs (register services + configure middleware). Since .NET 6 these were merged into a single, top-level Program.cs. If you see Startup.cs with ConfigureServices/Configure methods, you're looking at an older codebase — know both, because real projects still use the old style.
02

Program.cs, Line by Line

The entry point — what each line actually does

Here is a minimal-but-real Program.cs. Every line is doing something important; let's dissect it.

C#Program.cs
// 1 — Create the builder: sets up DI, config, logging, Kestrel
var builder = WebApplication.CreateBuilder(args);

// 2 — Register services into the DI container
builder.Services.AddControllers();
builder.Services.AddScoped<ITaskService, TaskService>();
builder.Services.AddDbContext<AppDbContext>(o =>
    o.UseSqlServer(builder.Configuration.GetConnectionString("Default")));

// 3 — Build the app (locks the DI container, creates the host)
var app = builder.Build();

// 4 — Configure the middleware pipeline (ORDER MATTERS)
if (app.Environment.IsDevelopment())
    app.UseSwagger().UseSwaggerUI();

app.UseHttpsRedirection();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

// 5 — Start Kestrel and block until shutdown
app.Run();
The five phases explained
1
CreateBuilder(args)
Reads configuration (appsettings.json, env vars, command line), sets up the logging providers, the DI container, and Kestrel defaults. Returns a WebApplicationBuilder.
2
builder.Services.Add…()
You register every service the app will need (controllers, your business services, DbContext, auth). This is "registration" — nothing is created yet, just recorded with a lifetime.
3
builder.Build()
Finalises the DI container and produces the WebApplication object (app). After this you can no longer register services.
4
app.Use… / app.Map…
You assemble the middleware pipeline in order. This defines how every request will be processed (your Module 4 material).
5
app.Run()
Starts Kestrel listening on its ports and blocks the main thread, keeping the app alive until shutdown (Ctrl+C / SIGTERM).
⚠️ Two different "Run"s — don't confuse them
app.Run() (no argument) at the bottom starts the server. app.Run(handler) (with a delegate) is a piece of terminal middleware. Same word, completely different jobs — a common interview gotcha.
03

Kestrel — The Web Server

The engine that turns network bytes into an HttpContext
3.1 — What Kestrel is

Kestrel is the cross-platform web server built into ASP.NET Core and written in C#. When you run dotnet run, Kestrel starts and listens on a port (e.g. https://localhost:5001). It accepts the raw TCP/HTTP connection, parses the incoming bytes into a structured HttpContext, hands that to your middleware pipeline, and writes the response back out to the socket.

📖 Mental model — the receptionist
Kestrel is the receptionist of your application. It's the first thing every request meets. It doesn't decide what to do with a request — it just receives it, packages it neatly as an HttpContext, and passes it inside to the pipeline. The response comes back out the same door.
3.2 — Why Kestrel instead of IIS?

Because IIS is Windows-only and Core had to run everywhere. Kestrel is fast, lightweight, and cross-platform, so the same app runs on Windows, Linux, and in containers. IIS becomes optional — in production it (or Nginx) typically sits in front of Kestrel as a reverse proxy.

1
Internet → Reverse Proxy (Nginx / IIS)
Handles TLS/SSL termination, load balancing, request filtering, serving static files, and shielding Kestrel from the open internet.
↓
2
Reverse Proxy → Kestrel
Forwards the request to your app's Kestrel server on an internal port.
↓
3
Kestrel → your ASP.NET Core app
Kestrel builds the HttpContext and runs the middleware pipeline.
📝 Interview answer — "Why a reverse proxy if Kestrel can self-host?"
Kestrel can face the internet directly (and does inside many containers), but a reverse proxy adds a hardened layer for TLS termination, load balancing across multiple app instances, request buffering, and protection against slow/malicious clients. So: Kestrel is the app server; Nginx/IIS is the edge.

The Request Lifecycle

The full journey — the answer to the #1 interview question

This is the diagram to be able to draw from memory. Follow a single call — GET /api/tasks/5 — all the way down and back up.

1
Client sends the HTTP request
Browser / mobile / Postman over HTTP(S).
↓
2
Kestrel receives it & builds an HttpContext
Parses raw bytes into Request/Response objects.
↓
3
Middleware pipeline runs in order
Exception handling → HTTPS → routing → authentication → authorization.
↓
4
Routing matches the endpoint; model binding runs
URL → controller action; request data → C# parameters.
↓
5
Controller → Service → Repository → Database
Controller is thin; service holds business logic; repository/EF Core hits SQL Server.
↑
6
Response flows back up through the middleware, then out via Kestrel
Each middleware can post-process; Kestrel writes the bytes back to the client.
💡 Say it in one breath
"The request hits Kestrel, which builds an HttpContext and passes it through the middleware pipeline. Routing selects the endpoint, model binding maps the data, the controller delegates to a service, the service uses a repository / EF Core to reach the database, and the response travels back up through the middleware and out through Kestrel." Nail that and you've answered the question every .NET interviewer asks.
05

HttpContext & the Host's Services

The per-request object and the infrastructure the host wires up
5.1 — What is HttpContext?

HttpContext is the object that represents everything about one HTTP request and its response. A fresh one is created by Kestrel for every request and discarded when it completes. It's how middleware and controllers read input and write output.

PropertyWhat it holds
RequestThe incoming method, path, headers, query string, and body.
ResponseThe outgoing status code, headers, and body you write.
UserThe authenticated user (a ClaimsPrincipal) — populated by authentication middleware.
ItemsA per-request dictionary to pass data between middleware/components.
RequestServicesThe per-request DI scope, used to resolve scoped services.
ConnectionLow-level info like the client's IP address.
📝 Interview-ready definition
"HttpContext represents all HTTP-specific information about a single request — its Request, Response, the authenticated User, per-request Items, and the DI scope (RequestServices). It's created per request and is the primary way middleware and controllers interact with the request and response."
5.2 — What the host gives you for free

Because CreateBuilder sets these up, you never wire them by hand — you just use them:

💉
DI Container
Constructor injection works everywhere — controllers, services, even middleware. (Module 5.)
⚙️
Configuration
appsettings.json + environment variables + more, layered by precedence. (Module 6.)
📋
Logging
ILogger<T> injectable anywhere, with multiple providers. (Module 7.)
🌐
Kestrel
Configured with sensible defaults; you rarely touch it early on.
06

Interview Preparation

Questions and model answers at the 4 YOE level
Q1Walk me through what happens when a request hits your ASP.NET Core API.
AKestrel receives the request and builds an HttpContext. It flows through the middleware pipeline in order — exception handling, HTTPS redirection, routing, authentication, authorization. Routing matches the URL to an endpoint, model binding maps the request data to action parameters, and the controller runs. The controller delegates to a service for business logic, which uses a repository or EF Core to reach the database. The response then travels back up through the middleware and Kestrel writes it to the client.
Q2What does WebApplication.CreateBuilder do?
AIt bootstraps the host: it reads configuration from appsettings.json, environment variables, and command-line args; sets up the logging providers; creates the dependency-injection container; and configures Kestrel with defaults. It returns a builder you use to register services before calling Build().
Q3Why doesn't ASP.NET Core need IIS anymore?
ABecause it ships its own cross-platform web server, Kestrel, and your app owns its own lifetime via Program.cs. IIS is now optional — in production it or Nginx usually acts as a reverse proxy in front of Kestrel for TLS termination, load balancing, and security, but it no longer hosts the app the way it did in Framework.
Q4What is HttpContext and what's its lifetime?
AIt's the object representing a single HTTP request and response — Request, Response, User, Items, and RequestServices (the per-request DI scope). Kestrel creates a new one per request, and it's disposed when the request completes. It should never be shared across requests or captured in a singleton.
Q5Difference between the old Startup.cs model and the minimal hosting model?
APre-.NET 6 split startup across Program.cs (build the host) and Startup.cs (ConfigureServices for DI, Configure for middleware). Since .NET 6 the minimal hosting model merges both into one top-level Program.cs: builder.Services for registration, then app.Use/Map for the pipeline. Functionally equivalent, just less boilerplate.
Q6What does app.Run() at the end of Program.cs do?
AIt starts Kestrel listening on its configured ports and blocks the main thread, keeping the application running until a shutdown signal (Ctrl+C or SIGTERM). Note it's different from app.Run(delegate), which registers terminal middleware.
