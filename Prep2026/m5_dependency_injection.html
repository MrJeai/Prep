01

The Problem DI Solves

Why creating your own dependencies hurts
1.1 — The tightly-coupled way

Consider a controller that needs a service. The obvious approach is to create it directly:

C#tightly coupled — bad
public class UserController
{
    // Controller creates its own dependency with 'new'
    private readonly UserService _service = new UserService();
}

This looks harmless but creates three real problems:

  • ✗Tight coupling: the controller is welded to the concrete UserService. To swap in a different implementation you must edit and recompile the controller.
  • ✗Untestable: you can't substitute a fake/mock UserService in a unit test, because the controller hard-codes the real one (which may hit a database).
  • ✗Hidden dependency chains: if UserService needs a repository, which needs a DbContext, the controller ends up responsible for constructing the whole graph.
1.2 — Inversion of Control & the DI solution

The fix is to stop creating dependencies and instead ask for them. The class declares what it needs (as an interface) in its constructor, and something external supplies it:

C#dependency injected — good
public class UserController
{
    private readonly IUserService _service;

    // The framework injects an IUserService — controller just asks
    public UserController(IUserService service)
    {
        _service = service;
    }
}
📖 Definition — IoC vs DI
Inversion of Control (IoC) is the broad principle: a class no longer controls the creation of its dependencies — that control is "inverted" to an external party. Dependency Injection is the specific technique that implements IoC by supplying dependencies through the constructor (or, less commonly, a method/property). The thing doing the supplying is the DI container. In short: DI is one way to achieve IoC.
💡 The benefits, in interview language
Loose coupling (depend on interfaces, not implementations), easy testing (inject mocks), easier maintenance (swap implementations in one place — the registration), and clear, explicit dependencies (the constructor documents exactly what a class needs).
02

How DI Works in ASP.NET Core

Register, resolve, and the object graph
2.1 — Step 1: Register services

In Program.cs you tell the container "when someone asks for this interface, give them this implementation, and keep it for this long":

C#Program.cs
builder.Services.AddScoped<IUserService, UserService>();
builder.Services.AddScoped<IUserRepository, UserRepository>();
builder.Services.AddSingleton<ICacheService, RedisCacheService>();
📝 Built-in, unlike Framework
In .NET Framework there was no DI container in the box — teams pulled in Autofac, Ninject, or Unity. ASP.NET Core ships a capable container as a first-class part of the framework. (You can still plug in Autofac for advanced features, but most apps never need to.)
2.2 — Step 2: The container resolves the graph

When a request arrives and the framework needs a UserController, the container looks at its constructor, sees it needs an IUserService, looks at that constructor, sees it needs an IUserRepository, and so on — recursively building the entire object graph for you.

1
Framework needs a UserController
Reads its constructor → needs IUserService
↓
2
Container creates UserService
Reads its constructor → needs IUserRepository
↓
3
Container creates UserRepository
Needs AppDbContext → creates it too
↑
4
Graph assembled bottom-up & injected
Fully-built controller handed to the framework.
💡 Use constructor injection, avoid the service locator
Always declare dependencies in the constructor. Resist the temptation to do HttpContext.RequestServices.GetService<T>() inside a method — that's the service locator anti-pattern: it hides dependencies, defeats testability, and is a known interview red flag.
03

Service Lifetimes

Transient, Scoped, Singleton — the most-asked DI question

When you register a service, you choose how long each instance lives. There are exactly three lifetimes, and choosing correctly is both a correctness and a performance concern.

Transient
New instance every time it's requested — even twice within the same request.
  • Use for: lightweight, stateless services.
  • Method: AddTransient
Scoped
One instance per HTTP request, shared throughout that request, then disposed.
  • Use for: DbContext, business/repository services. The default choice.
  • Method: AddScoped
Singleton
One instance for the entire app lifetime, shared across all requests & users.
  • Use for: caches, config, stateless thread-safe helpers.
  • Method: AddSingleton
LifetimeCreatedShared across requests?Typical use
TransientEvery single resolutionNoCheap, stateless helpers, mappers
ScopedOnce per HTTP requestNo (per-request)DbContext, services, repositories
SingletonOnce for the appYes (all requests)Caching, configuration, in-memory state
📝 Why DbContext is Scoped
EF Core's DbContext tracks changes for a single unit of work and is not thread-safe. Scoped gives each request its own context (so concurrent requests don't corrupt each other) while sharing one context across everything within that request (so all your repositories enrol in the same transaction). Singleton would be shared across all requests — a bug. Transient would give each repository a different context — also a bug. Scoped is exactly right.
04

Lifetime Pitfalls

The captive dependency — the classic interview trap
4.1 — The captive dependency

The cardinal rule: a longer-lived service must never capture a shorter-lived one. The dangerous case is injecting a Scoped (or Transient) service into a Singleton.

🚫 Why it's a bug
A Singleton is created once and lives forever. If it holds a reference to a Scoped service (like a DbContext), that "per-request" object is now trapped inside the Singleton for the whole app lifetime — it's never disposed, it leaks resources (e.g. a DB connection), and it's shared across every request even though it was meant to last one. This is called a captive dependency.
Singleton injects…Scoped injects…Transient injects…
Singleton ✅Singleton ✅Singleton ✅
Scoped ❌ (captive!)Scoped ✅Scoped ✅
Transient ⚠️ (captured)Transient ✅Transient ✅
💡 How the framework helps
In Development, ASP.NET Core runs scope validation at startup and throws if a Singleton tries to consume a Scoped service — catching the mistake before it ships. If you genuinely need a scoped service inside a singleton, inject an IServiceScopeFactory and create a scope explicitly when you need the work done.
4.2 — Scoped services in middleware

A related trap (covered in your Middleware module): middleware is built once, so its constructor behaves like a singleton. Never inject a Scoped service into a middleware constructor — inject it as a parameter of InvokeAsync(HttpContext, IMyScopedService) instead, which resolves it from the per-request scope.

05

Advanced Patterns

Factory registration, multiple implementations, IOptions
5.1 — Factory registration

When creating a service needs logic or other services, register it with a factory lambda:

C#
builder.Services.AddScoped<IPaymentGateway>(sp =>
{
    var config = sp.GetRequiredService<IConfiguration>();
    return new StripeGateway(config["Stripe:Key"]);
});
5.2 — Multiple implementations of one interface

Register several, then inject them all as IEnumerable<T> — useful for things like a set of validators or notification channels (email, SMS, push):

C#
builder.Services.AddScoped<INotifier, EmailNotifier>();
builder.Services.AddScoped<INotifier, SmsNotifier>();
// Inject IEnumerable<INotifier> to get both
5.3 — IOptions for typed configuration

Configuration sections bind to strongly-typed classes and are injected via IOptions<T> — registered through DI. (Full detail in Module 6.) The key point: typed config is delivered through the DI system, which is why it ties in here.

C#
builder.Services.Configure<JwtSettings>(
    builder.Configuration.GetSection("Jwt"));
// Then inject IOptions<JwtSettings> anywhere
06

Interview Preparation

Questions and model answers at the 4 YOE level
Q1What is Dependency Injection and what problem does it solve?
ADI is a technique where a class receives its dependencies from an external source instead of creating them itself. It solves tight coupling: by depending on interfaces and having the container supply implementations, classes become easy to test (inject mocks), easy to maintain (swap implementations in one place), and have explicit, visible dependencies. It's the concrete way ASP.NET Core implements Inversion of Control.
Q2Explain Transient, Scoped, and Singleton with examples.
ATransient creates a new instance on every resolution — good for lightweight stateless helpers. Scoped creates one instance per HTTP request, shared within that request — the default for business services and DbContext. Singleton creates one instance for the whole application, shared across all requests — good for caches and configuration. The key is matching lifetime to the service's state and thread-safety needs.
Q3Why is EF Core's DbContext registered as Scoped?
ABecause DbContext is a unit of work and isn't thread-safe. Scoped gives each request its own context so concurrent requests don't interfere, while sharing a single context across all components within that request so they participate in the same change tracker and transaction. Singleton would share it across all requests (unsafe); Transient would give each repository a different context (breaks the unit of work).
Q4What is a captive dependency?
AIt's when a longer-lived service captures a shorter-lived one — classically injecting a Scoped service into a Singleton. The scoped object then lives as long as the singleton (the whole app), so it's never disposed, leaks resources, and is wrongly shared across requests. ASP.NET Core's scope validation catches this at startup in Development. The fix is to inject an IServiceScopeFactory and create a scope when needed.
Q5What's the difference between IoC and DI?
AIoC is the general principle — control over creating dependencies is inverted away from the class to an external party. DI is a specific implementation of IoC where dependencies are supplied, typically through the constructor, by a container. So every DI is IoC, but IoC also includes other techniques.
Q6What's wrong with the service locator pattern?
ACalling the container directly inside a method (e.g. RequestServices.GetService<T>()) hides a class's real dependencies — they're no longer visible in the constructor — which makes the code harder to understand and to unit test, since you can't simply pass in mocks. Prefer constructor injection so dependencies are explicit.
