01

Authentication vs Authorization

Two different questions, asked in order
🪪
Authentication (AuthN)
Who are you? Verifying identity — checking credentials or a token. The result: a known (or anonymous) user.
🚦
Authorization (AuthZ)
What are you allowed to do? Deciding whether the now-identified user may access this resource or action.
📖 Always in this order
Authentication happens first (establish identity), then authorization (check permission). This maps directly to status codes from Module 1: failing AuthN → 401 Unauthorized ("we don't know you"); passing AuthN but failing AuthZ → 403 Forbidden ("we know you, but no").
02

JWT Deep Dive

The stateless token that powers modern APIs
2.1 — What a JWT is

A JWT (JSON Web Token) is a compact, signed token that carries claims about a user. It has three Base64URL-encoded parts separated by dots: header.payload.signature.

JWT
// Header — algorithm & type
{ "alg": "HS256", "typ": "JWT" }
// Payload — claims (statements about the user)
{ "sub": "42", "name": "Asha", "role": "Admin", "exp": 1718000000 }
// Signature = HMACSHA256(base64(header) + "." + base64(payload), secret)
📖 Definition — Claim
A claim is a key-value statement about the subject, e.g. role: Admin or sub: 42. Standard claims include sub (subject/user id), exp (expiry), iss (issuer), aud (audience). In ASP.NET Core these become the User (a ClaimsPrincipal) on HttpContext.
2.2 — Why JWT is stateless & how validation works

The server signs the token with a secret (HMAC) or private key (RSA). On each request the client sends it in the Authorization: Bearer <token> header. The server re-computes the signature and compares — if it matches and the token hasn't expired, the user is authenticated. No database lookup, no server session.

⚠️ Signed ≠ encrypted
A JWT's payload is only Base64-encoded, not encrypted — anyone can read it. The signature guarantees it wasn't tampered with, not that it's secret. So never put sensitive data (passwords, secrets) in a JWT, and always send it over HTTPS.
💡 Connects to REST statelessness (Module 1)
This is why APIs send a token on every request instead of keeping a server session — it keeps the API stateless and horizontally scalable. Any server can validate any token with just the shared secret.
03

The Auth Flow in ASP.NET Core

Middleware order and the [Authorize] attribute

Two middleware components do the work, and order matters — authentication must run before authorization (you can't check permissions for someone you haven't identified).

C#Program.cs
builder.Services.AddAuthentication("Bearer")
    .AddJwtBearer(opt => { /* validate issuer, audience, key, lifetime */ });
builder.Services.AddAuthorization();
// ... pipeline ...
app.UseAuthentication();   // 1) who are you?  → sets HttpContext.User
app.UseAuthorization();    // 2) are you allowed? → enforces [Authorize]
C#
[Authorize]                       // any authenticated user
[Authorize(Roles = "Admin")]      // must have the Admin role
[AllowAnonymous]                 // opt a specific action back out
public class OrdersController : ControllerBase { }
📝 What UseAuthentication does
It reads the Bearer token, validates the signature/issuer/audience/expiry, builds a ClaimsPrincipal, and assigns it to HttpContext.User. After that, UseAuthorization and [Authorize] can make decisions based on those claims.

Roles, Policies & Claims

Three ways to express "who can do what"
ApproachHowBest for
Role-based[Authorize(Roles="Admin")]Simple, coarse buckets of users
Claims-basedRequire a specific claim valueFine-grained attributes (department, plan tier)
Policy-basedNamed policy with requirementsReusable, complex rules — the modern default
C#policy example
builder.Services.AddAuthorization(o =>
    o.AddPolicy("Over18", p => p.RequireClaim("age", /* ... */)));
// usage
[Authorize(Policy = "Over18")]
💡 Roles are really just claims
Under the hood a role is a claim of type role. Policies are the most flexible: they can combine multiple claim checks, custom requirements, and handlers. Saying "I'd reach for policy-based authorization for anything beyond a trivial role check" reads as senior.

Refresh Tokens & OAuth/OIDC

Token lifetimes and the delegated-auth picture
5.1 — Access tokens vs refresh tokens

A JWT access token is deliberately short-lived (minutes) — if stolen, it expires fast. But forcing users to log in every few minutes is awful. The fix: a long-lived refresh token, stored securely, that the client exchanges for a new access token when the old one expires.

1
Login → server returns access token (short) + refresh token (long)
↓
2
Access token expires → client sends refresh token to a /refresh endpoint
↓
3
Server validates it (often stored server-side so it can be revoked) → issues a fresh access token
📝 The trade-off, stated
Access tokens are stateless and fast but can't be revoked before expiry — so keep them short. Refresh tokens are usually stored server-side precisely so they can be revoked (logout, compromise). This split balances scalability with control.
5.2 — OAuth 2.0 & OpenID Connect (overview)

OAuth 2.0 is a framework for delegated authorization — letting an app act on your behalf without your password ("Sign in with Google" granting limited access). OpenID Connect (OIDC) is a thin identity layer on top of OAuth 2.0 that adds authentication (an ID token proving who you are). Rule of thumb: OAuth = authorization/access; OIDC = "who is this user". You don't need to implement these from scratch — know what they're for.

💡 Security hygiene to mention
Always HTTPS · hash passwords with a strong algorithm (bcrypt/Argon2/PBKDF2), never store plaintext · short access-token lifetimes · validate issuer/audience/signature · principle of least privilege. A nod to the OWASP Top 10 (injection, broken auth, etc.) shows breadth.

Interview Preparation

Questions and model answers at the 4 YOE level
Q1Authentication vs authorization?
AAuthentication verifies who you are (identity, via credentials or a token); authorization decides what you're allowed to do once identified. AuthN runs first. Failing AuthN gives 401; passing AuthN but failing AuthZ gives 403.
Q2What is a JWT and how is it validated?
AA compact signed token with three parts — header, payload (claims), and signature. The server signs it with a secret or private key; on each request the client sends it as a Bearer token and the server recomputes the signature to verify it wasn't tampered with and checks expiry. It's stateless, so no DB lookup or session is needed.
Q3Is a JWT encrypted?
ANo — by default it's only Base64-encoded and signed, so the payload is readable by anyone. Signing guarantees integrity, not secrecy. So you never put sensitive data in it and always use HTTPS.
Q4Why use refresh tokens?
AAccess tokens are kept short-lived so a stolen one expires quickly, but you don't want users logging in constantly. A long-lived refresh token, usually stored server-side so it can be revoked, is exchanged for a new access token when the old one expires — balancing scalability with the ability to revoke.
Q5Role-based vs policy-based authorization?
ARole-based checks a simple role claim like [Authorize(Roles="Admin")] — good for coarse buckets. Policy-based defines named, reusable rules that can combine multiple claim checks and custom requirements. Roles are really just claims; policies are the flexible modern approach for anything non-trivial.
Q6Difference between OAuth and OpenID Connect?
AOAuth 2.0 is a delegated authorization framework — granting an app limited access on your behalf. OpenID Connect is an identity layer on top of OAuth that adds authentication via an ID token. OAuth answers "what can this app access"; OIDC answers "who is this user".
