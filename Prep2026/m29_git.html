Git is a distributed version control system: every clone has the full history, so you can commit, branch, and view history offline, then sync with the remote. A commit is an immutable snapshot identified by a hash; a branch is just a movable pointer to a commit.

📖 Why "distributed" matters
Unlike older centralised systems, there's no single point of failure for history, and most operations are local and fast. Branches are cheap pointers, which is why Git workflows lean so heavily on branching.
02

Branching: Merge vs Rebase

The question everyone gets asked
Merge
Combines branches with a merge commit, preserving the true history (and the branch shape).
  • Non-destructive; history is accurate but can look tangled.
Rebase
Replays your commits on top of another branch, creating a linear history.
  • Clean, straight line; but rewrites commit hashes.
🚫 The golden rule of rebase
Never rebase commits that have been pushed and shared. Rebasing rewrites history, so shared commits get new hashes and you force teammates into painful conflicts. Rebase your local, unpushed work to tidy it; merge (or merge via PR) to integrate shared branches. Stating this rule is the whole point of the question.
💡 Practical workflow
Many teams rebase a feature branch onto the latest main locally to keep it current and linear, then open a PR that merges (often a squash-merge) into main. Best of both: clean feature history, safe integration.

Power Tools

Cherry-pick, squash, stash, reset vs revert
CommandWhat it doesWhen
git cherry-pick <hash>Apply one specific commit onto the current branchPort a single fix to another branch
git rebase -iInteractive: reorder, edit, squash commitsClean up local history before a PR
git stashShelve uncommitted changes temporarilySwitch context without committing WIP
git revert <hash>New commit that undoes a commitSafe on shared branches
git resetMove branch pointer back (soft/mixed/hard)Local only — rewrites history
⚠️ revert vs reset — the safe-vs-dangerous pair
revert adds a new commit that cancels a previous one, leaving history intact — safe to push. reset rewinds the branch pointer (and with --hard, discards changes), rewriting history — fine locally, dangerous on a shared branch. To undo something already pushed, use revert.

Conflicts & Branching Strategies

Resolving clashes and organising a team
4.1 — Merge conflicts

A conflict happens when two branches change the same lines and Git can't auto-merge. Git marks the regions with <<<<<<< / ======= / >>>>>>>; you edit to the desired result, remove the markers, git add the file, and continue. The fix is human judgment — Git just shows you both sides.

4.2 — Branching strategies
StrategyIdea
Trunk-basedShort-lived branches merged to main frequently; pairs with CI/CD (Module 22). Popular today.
GitHub FlowBranch off main → PR → review → merge → deploy. Simple, common.
GitflowLong-lived develop/release/hotfix branches. Heavier; suits scheduled releases.
💡 Tie it to delivery
Frequent integration (trunk-based / GitHub Flow) means smaller merges, fewer conflicts, and faster CI/CD — connecting straight back to Module 22. Mention that link.
05

Interview Preparation

Questions and model answers at the 4 YOE level
Q1Merge vs rebase?
AMerge combines branches with a merge commit and preserves the true history, which can look tangled. Rebase replays your commits on top of another branch for a clean linear history but rewrites commit hashes. The golden rule is to never rebase commits that have been pushed and shared, because rewriting shared history forces painful conflicts on teammates. I rebase local work to tidy it and merge to integrate.
Q2How do you undo a commit that's already pushed?
AWith git revert, which creates a new commit that cancels the bad one while leaving history intact, so it's safe to push. I avoid git reset on shared branches because it rewrites history; reset is fine only for local, unpushed work.
Q3What's cherry-pick for?
AApplying a single specific commit from one branch onto another by its hash — handy for porting an isolated bug fix to a release branch without merging everything else from the source branch.
Q4How do you resolve a merge conflict?
AGit marks the conflicting regions with conflict markers showing both sides. I edit the file to the intended result, remove the markers, stage it with git add, and continue the merge or rebase. Git can't decide the logic — it just surfaces both versions for me to reconcile.
Q5What is interactive rebase used for?
Agit rebase -i lets me reorder, edit, drop, or squash commits — most often to squash several messy work-in-progress commits into one clean commit before opening a pull request. I only do this on local, unpushed commits.
