Cloud Basics

Why cloud, and the service models

The cloud gives you on-demand infrastructure you rent instead of own: no buying servers, pay for what you use, scale up or down on demand, and rely on the provider for availability and global reach. Services come in three models, from most to least responsibility on you:

ModelYou manageExample
IaaS (Infrastructure)OS, runtime, app — just rent VMsAzure Virtual Machines
PaaS (Platform)Just your app & data; platform handles servers/OSAzure App Service
SaaS (Software)Nothing — just use itMicrosoft 365
💡 For a .NET API, PaaS is the sweet spot
App Service lets you deploy your app without managing servers, OS patches, or load balancers — Azure handles the plumbing while you focus on code. That's the default recommendation unless you specifically need container orchestration or low-level control.

📝 The pattern to notice
Every Phase-2 concept has a managed Azure equivalent: cache → Azure Cache for Redis, broker → Service Bus, DB → Azure SQL, secrets → Key Vault. "Managed" means Azure runs and patches it; you just consume it.
03

Config, Key Vault & Managed Identity

Secrets done right in the cloud

App Service exposes Application Settings that surface as environment variables — so your configuration providers (Module 6) pick them up with no code change. For real secrets, store them in Key Vault and have the app read them at startup.

📖 Managed Identity — no secrets to manage
The cleanest pattern: give the App Service a managed identity — an Azure-managed credential — and grant it access to Key Vault and Azure SQL. The app authenticates as itself with no connection string passwords or API keys to store or rotate. This is the gold-standard answer to "how do you handle secrets in production."

Deploying & Scaling

Getting the app live and handling load
4.1 — Deployment options
  • ✓CI/CD push — GitHub Actions deploys on merge (Module 22) — the standard.
  • ✓Container — push your Docker image (Module 21) to Azure Container Registry and run it on App Service or Container Apps.
  • ✓Deployment slots — deploy to a "staging" slot, warm it up, then swap into production with near-zero downtime and instant rollback.
4.2 — Scaling
TypeWhat
Scale up (vertical)Bigger instance — more CPU/RAM. Limited by max size.
Scale out (horizontal)More instances behind a load balancer. Can autoscale on metrics.
⚠️ Scaling out needs stateless apps
Autoscaling to many instances only works if the app holds no local state — session and cache must be external (Redis), exactly the lesson from Modules 1 and 17. This is why statelessness keeps coming up.
05

Monitoring

Knowing what production is doing

Application Insights (part of Azure Monitor) collects request rates, response times, failures, dependencies (DB/HTTP calls), and traces — giving you dashboards and alerts so you find problems before users report them. It integrates with ASP.NET Core with minimal setup and ties directly into the production logging and observability of Module 24.

💡 What to mention
"I'd wire up Application Insights for request/dependency telemetry and set alerts on error rate and latency, plus health checks so the platform can restart unhealthy instances." That sentence signals production awareness.

Interview Preparation

Questions and model answers at the 4 YOE level
Q1IaaS vs PaaS vs SaaS — and which for a .NET API?
AIaaS rents raw infrastructure like VMs where you manage the OS and runtime; PaaS gives you a managed platform where you deploy just your app and data; SaaS is finished software you just use. For a .NET API I'd choose PaaS — Azure App Service — so I focus on code while Azure handles servers, patching, and load balancing, unless I need container orchestration or low-level control.
Q2Which Azure services would you use for a typical backend?
AApp Service to host the API, Azure SQL Database for data, Azure Cache for Redis for distributed caching, Blob Storage for files, Key Vault for secrets, and Service Bus if I need messaging. Each is the managed equivalent of a building block — Azure runs and patches it while I consume it.
Q3How do you handle secrets and connection strings in Azure?
ANon-secret config goes in App Service application settings, which surface as environment variables my config providers read automatically. Real secrets live in Key Vault. Best of all, I give the App Service a managed identity and grant it access to Key Vault and Azure SQL, so the app authenticates as itself with no passwords or keys to store or rotate.
Q4Scale up vs scale out, and what does scaling out require?
AScale up means a bigger instance with more CPU and RAM; scale out means more instances behind a load balancer, which can autoscale on metrics. Scaling out requires the app to be stateless — session and cache must live externally in something like Redis — otherwise users get inconsistent behaviour across instances.
Q5How would you deploy with zero downtime?
AUse App Service deployment slots: deploy the new version to a staging slot, warm it up and verify, then swap it into production. The swap is near-instant and, if something's wrong, I can swap back immediately for a fast rollback. The deploy itself is automated through the CI/CD pipeline.
