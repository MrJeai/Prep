Caching & Redis

Caching is the highest-leverage performance tool in backend engineering, and Redis is the tool everyone reaches for. Interviewers probe whether you understand the patterns and — crucially — the hard parts: invalidation and stampedes. This module builds from "why a cache helps" to running Redis behind an ASP.NET Core API.

Interview ROI: Very High

01

Why Cache

Trading freshness for speed

A cache stores the result of an expensive operation so the next request can return it instantly instead of recomputing or re-querying. The win is dramatic: a database call might take ~50–200 ms while a cache hit takes ~1–5 ms, and it removes load from the database — often the scarcest resource.

📖 The core trade-off
Caching trades freshness for speed. Cached data can be slightly stale. So you cache data that's read often and changes rarely (product catalogues, config, reference data), and you think carefully about when to invalidate. The hard part of caching isn't storing — it's knowing when the stored copy is wrong.
02

In-Memory vs Distributed

Two scopes, two use cases
In-Memory (IMemoryCache)
Stored in the app process's RAM.
  • Fastest; no network hop.
  • Lost on restart; not shared across instances.
Distributed (Redis)
A separate cache server shared by all app instances.
  • Shared & survives app restarts.
  • Small network cost; needs infra.
⚠️ The scaling gotcha interviewers love
In-memory cache breaks when you scale to multiple instances: instance A caches a value, instance B doesn't have it, and a load balancer sends users to either — so they see inconsistent data. Once you run more than one instance, you need a distributed cache like Redis. This connects to REST statelessness (Module 1): shared state lives outside the app.

Caching Patterns

How reads and writes interact with the cache
3.1 — Cache-Aside (the default)

The application manages the cache: check it first; on a miss, load from the DB and populate the cache. By far the most common pattern.

Store in cache with a TTL, then return. (Hit next time.)
3.2 — Other patterns
PatternIdea
Read-throughThe cache itself loads from the DB on a miss (library/cache handles it, not your code).
Write-throughWrites go to cache and DB together — cache always fresh, writes slower.
Write-behindWrite to cache now, persist to DB asynchronously later — fast, but risk of loss.
04

TTL, Eviction & Invalidation

The genuinely hard parts

TTL (time to live) sets how long an entry stays before expiring — the simplest way to bound staleness. Eviction is what the cache does when it's full (e.g. LRU — evict the least recently used). Invalidation is actively removing/updating an entry when the underlying data changes.

🚫 Cache stampede (thundering herd)
When a popular key expires, many requests miss simultaneously and all hit the database at once — a spike that can overwhelm it. Mitigations: a short lock so only one request repopulates while others wait, slightly randomised ("jittered") TTLs so keys don't expire together, or refreshing hot keys before they expire. Naming this problem unprompted is a strong senior signal.
💡 "There are only two hard things…"
The famous quip — cache invalidation and naming things — is true. Stale data bugs are subtle. Strategies: TTL (accept brief staleness), explicit invalidation on write, or versioned keys. State which you'd choose and why.
05

Redis in ASP.NET Core

What Redis is and how to wire it up

Redis is an in-memory key-value data store, commonly used as a distributed cache (it also does pub/sub, counters, sorted sets, and more). It's extremely fast because data lives in RAM. ASP.NET Core abstracts caching behind IDistributedCache, with a Redis implementation you register at startup.

C#Program.cs
builder.Services.AddStackExchangeRedisCache(o =>
    o.Configuration = builder.Configuration.GetConnectionString("Redis"));
C#cache-aside with IDistributedCache
var cached = await _cache.GetStringAsync(key);
if (cached is not null) return JsonSerializer.Deserialize<Product>(cached);

var product = await _db.Products.FindAsync(id);   // miss → load
await _cache.SetStringAsync(key, JsonSerializer.Serialize(product),
    new() { AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10) });
return product;
📝 Pick the abstraction by scope
IMemoryCache for single-instance in-process caching; IDistributedCache (Redis) once you scale out. Same idea, different scope.
06

Interview Preparation

Questions and model answers at the 4 YOE level
Q1When should you cache, and what's the trade-off?
ACache data that's read often and changes rarely — reference data, catalogues, config. The trade-off is freshness for speed: cached data can be stale, so the hard part is invalidation. A cache hit is roughly 1–5ms versus 50–200ms for a database call, and it offloads the database.
Q2In-memory vs distributed cache?
AIn-memory (IMemoryCache) lives in the app process — fastest but lost on restart and not shared across instances. Distributed (Redis) is a separate shared server, slightly slower due to the network hop but consistent across all instances. Once you run more than one instance you need a distributed cache, otherwise users get inconsistent data depending on which instance serves them.
Q3Explain the cache-aside pattern.
AThe application checks the cache first; on a miss it loads from the database, stores the result in the cache with a TTL, and returns it. Subsequent reads hit the cache. It's the most common pattern because the app stays in control of what's cached and for how long.
Q4What is a cache stampede and how do you prevent it?
AWhen a hot key expires, many requests miss at the same time and all hit the database simultaneously, causing a spike. You prevent it with a lock so only one request repopulates while others wait, jittered TTLs so keys don't all expire together, or proactively refreshing hot keys before expiry.
Q5How do you handle cache invalidation?
AThree common strategies: rely on a TTL and accept brief staleness; explicitly remove or update the entry when the underlying data is written; or use versioned keys so a new version naturally bypasses the old. The right choice depends on how fresh the data must be versus how often it changes.
