Logging Fundamentals

When something breaks in production at 2 a.m., logs are the only thing standing between you and guesswork. ASP.NET Core has a clean, built-in logging abstraction with levels, structured output, and pluggable destinations. This module covers using it well — and the single most important habit: structured logging.

Interview ROI: Medium
Real-world: Essential
Week 1 · Phase 1
01

Why Logging Matters

The difference between debugging and guessing in production

You can't attach a debugger to production. Logs are how you understand what your application actually did: which requests came in, what decisions the code made, where it slowed down, and exactly what failed and why. Good logging turns "the site is broken, no idea why" into "request X failed at the payment step with this exception." That difference is the job.

📖 The logging abstraction
ASP.NET Core gives you ILogger<T> — an abstraction over logging. Your code logs against the interface; where the logs actually go (console, file, a cloud service) is decided separately by providers. This means you can change destinations without touching a single line of your logging code — the same loose-coupling idea as DI.
02

The ILogger Abstraction

Inject it, and the category comes for free

You get a logger the same way you get any dependency — inject ILogger<T>, where T is the current class. The class name becomes the log's category, so you can later filter logs by where they came from.

C#
public class TaskService
{
    private readonly ILogger<TaskService> _logger;

    public TaskService(ILogger<TaskService> logger)
    {
        _logger = logger;   // category = "MyApp.Services.TaskService"
    }

    public void Process(int id)
    {
        _logger.LogInformation("Processing task {TaskId}", id);
    }
}
📝 Architecture in one line
ILogger (what you call) → ILoggerProvider (a destination, e.g. Console) → the output sink. One log call can fan out to several providers at once.
03

Log Levels

Six severities — and choosing the right one

Every log entry has a level indicating its severity. Levels let you record everything in development but only the important things in production, just by changing configuration.

LevelMeaningUse for
TraceMost detailed; may contain sensitive dataDeep diagnostics, never in production
DebugDeveloper debugging infoLocal development
InformationNormal flow of the app"Order created", "User logged in"
WarningSomething unexpected but recoverableRetry happened, deprecated path used
ErrorA failure in the current operationCaught exception, request failed
CriticalApp-wide failureOut of disk, DB unreachable on startup

You set the minimum level (globally and per category) in configuration. Anything below the threshold is discarded cheaply:

JSONappsettings.json
{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  }
}
💡 The Microsoft category trick
Framework logs are noisy. Setting "Microsoft.AspNetCore": "Warning" silences routine framework chatter while keeping your own app at Information — a clean, signal-rich log.
04

Structured Logging

The single most important logging habit

This is the concept that separates professional logging from amateur logging. Don't build your log message with string concatenation or interpolation — use message templates with named placeholders.

❌
Don't: interpolate / concatenate
_logger.LogInformation($"User {userId} placed order {orderId}");
→ Produces a flat string. The userId and orderId are lost as searchable data.
✅
Do: message template with named values
_logger.LogInformation("User {UserId} placed order {OrderId}", userId, orderId);
→ The logging system captures UserId and OrderId as named fields you can filter and query on.
📖 Definition — Structured logging
Structured logging records each log as an event with named, typed properties (not just a sentence). When stored in a system like Seq, Elasticsearch, or Application Insights, you can then run queries like "show all logs where OrderId = 42" or "count errors by UserId" — impossible with plain text. The placeholders are matched to arguments by position, so order matters, but the names are what make them queryable.
4.1 — Logging exceptions correctly

Pass the exception as the first argument so the full stack trace is captured as structured data, not flattened into the message:

C#
try { ... }
catch (Exception ex)
{
    _logger.LogError(ex, "Failed to process order {OrderId}", orderId);
}
05

Providers & Serilog

Where logs go — and the most popular production library

Built-in providers include Console, Debug, EventSource, and (on Windows) EventLog. These are fine for development, but production usually wants logs written to files and shipped to a central system you can search.

5.1 — Serilog (the de-facto standard)

Serilog is the most widely used third-party logging library for .NET. It plugs into the same ILogger abstraction, so your logging code doesn't change — you just configure Serilog at startup and choose sinks (destinations): console, rolling files, Seq, Elasticsearch, Application Insights, and many more.

📖 Definition — Sink
A sink is a Serilog output destination. One log event can be written to several sinks at once — e.g. pretty-printed to the console and shipped as JSON to a central store for searching. Because Serilog is structured-first, it's a natural fit for the structured logging from Chapter 4.
📝 Scope: foundations now, production later
For Week 1, the goal is using ILogger well with proper levels and structured messages. Full production observability — Serilog configuration, correlation IDs, health checks, log aggregation — is its own module later in the roadmap (M24). Just know Serilog is where most teams land.

Interview Preparation

Questions and model answers at the 4 YOE level
Q1How does logging work in ASP.NET Core?
AIt's built around the ILogger abstraction. You inject ILogger<T> and log against it; the class name becomes the log category. Separately, one or more providers decide where logs go — console, debug, files, or cloud services via libraries like Serilog. Because code logs against the abstraction, you can change destinations without changing logging code.
Q2What is structured logging and why prefer it?
AIt's logging events with named properties rather than flat strings — using message templates like LogInformation("Order {OrderId} created", id) instead of interpolating the value into the string. The benefit is that OrderId is captured as queryable data, so in a log store you can filter and aggregate on it. Interpolation throws that structure away.
Q3Walk through the log levels.
ATrace (most detailed, never in prod), Debug (dev debugging), Information (normal flow like "user logged in"), Warning (unexpected but recoverable), Error (a failed operation, usually with an exception), and Critical (app-wide failure). You set a minimum level globally and per category in configuration, so production can run at Information while development runs at Debug.
Q4How do you log an exception properly?
APass the exception as the first argument to LogError, e.g. LogError(ex, "Failed processing {OrderId}", id). That captures the full stack trace as structured data rather than losing it inside a concatenated string, and keeps the message template's named properties queryable.
Q5What is Serilog and why is it popular?
ASerilog is the most popular third-party .NET logging library. It's structured-first and plugs into the standard ILogger abstraction, so your code is unchanged. You configure sinks — destinations like console, rolling files, Seq, or Application Insights — and a single event can go to several at once, which makes centralised, searchable production logging easy.
