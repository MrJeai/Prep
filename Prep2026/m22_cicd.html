CI/CD with GitHub Actions

CI/CD is how modern teams ship safely and often — every push is automatically built, tested, and deployed. You won't be grilled deeply at 4 YOE, but you're expected to explain the pipeline, read a workflow file, and know where tests and secrets fit. 01

What CI/CD Is

Continuous Integration & Continuous Delivery/Deployment
🔗
CI — Continuous Integration
Every push is automatically built and tested, so integration problems surface within minutes, not at release.
🚚
CD — Continuous Delivery
Every passing build is ready to deploy — release is a button press.
🚀
CD — Continuous Deployment
Goes further: every passing build is automatically deployed to production.
📖 Why it matters
CI/CD replaces risky, infrequent manual releases with small, automated, frequent ones. Smaller changes are easier to test, review, and roll back — so teams ship faster and more safely. The automated tests from Module 16 are what make this trustworthy.

03

GitHub Actions Workflow

Triggers, jobs, steps, runners

GitHub Actions runs workflows defined as YAML files in .github/workflows/. A workflow has triggers (when to run), one or more jobs (which run on runners — VMs), and each job has steps (commands or reusable actions).

YAML.github/workflows/ci.yml
name: CI
on:
  push: { branches: [main] }
  pull_request:                 # also run on PRs
jobs:
  build-test:
    runs-on: ubuntu-latest      # the runner
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with: { dotnet-version: '8.0.x' }
      - run: dotnet restore
      - run: dotnet build --no-restore -c Release
      - run: dotnet test --no-build       # fails the job if tests fail
📝 Vocabulary cheat sheet
Workflow = the whole automated process · Job = a group of steps on one runner (jobs can run in parallel) · Step = a single command or action · Action = a reusable building block (e.g. actions/checkout) · Runner = the machine that executes a job.
04

CD: Deploy & Secrets

From a passing build to running in production

After CI passes, the CD stage publishes an artifact (a build output or a Docker image pushed to a registry) and deploys it — for a .NET app, often to Azure App Service or a container host (ties to Modules 21 & 23). Deployment needs credentials, which must never be hard-coded.

🚫 Secrets never live in the repo
API keys, connection strings, and cloud credentials go in GitHub Secrets (encrypted repo/environment settings) and are referenced as ${{ secrets.AZURE_CREDENTIALS }} — never committed to source. This is the same secret-management discipline as Module 6's config and Key Vault.
💡 Environments & gates
GitHub environments (e.g. staging, production) can require approvals before a deploy proceeds, so production releases get a human checkpoint while staging deploys freely.
05

Best Practices

Pipelines that teams trust
  • ✓Keep CI fast — minutes, not hours; cache dependencies. Slow pipelines get ignored.
  • ✓Run on every PR — catch issues before merge, not after.
  • ✓Branch protection — require green CI + review before merging to main.
  • ✓One artifact, many environments — build once, promote the same artifact through staging → prod.
  • ✓Plan rollback — be able to redeploy the previous version quickly.
06

Interview Preparation

Questions and model answers at the 4 YOE level
Q1What's the difference between CI, continuous delivery, and continuous deployment?
ACI means every push is automatically built and tested so integration issues surface immediately. Continuous delivery means every passing build is kept ready to release at the push of a button. Continuous deployment goes further and automatically releases every passing build to production. The progression is build/test → release-ready → auto-release.
Q2Walk me through a typical pipeline.
ACheckout the code, restore and build, run unit and integration tests, publish an artifact or Docker image, then deploy to an environment. If any stage fails the pipeline stops, so a broken change never reaches production. The PR shows the build status so reviewers know it's safe to merge.
Q3What are the building blocks of a GitHub Actions workflow?
AA workflow is YAML in .github/workflows triggered by events like push or pull_request. It contains jobs that run on runners, and each job has steps that are either shell commands or reusable actions like actions/checkout. Jobs can run in parallel, steps run in order.
Q4How do you handle secrets in a pipeline?
ASecrets like cloud credentials and connection strings go in GitHub Secrets — encrypted settings referenced as ${{ secrets.NAME }} — never committed to the repo. It's the same principle as keeping config and secrets out of source code and in environment variables or a vault.
Q5How would you make deployments safer?
ARequire green CI and a review via branch protection before merging, deploy small frequent changes, use environments with approval gates for production, build one artifact and promote it through staging to prod, and have a fast rollback by redeploying the previous version.
